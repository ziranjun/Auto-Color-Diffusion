# Auto Color Diffusion —— AI 批量调色辅助工具

用 AI 为一批 RAW 照片生成 Adobe Camera Raw（ACR）调整参数，写出 XMP 旁侧文件，
再生成 Photoshop 批量导出脚本。**只改调色参数，绝不覆盖你已有的蒙版与修图成果。**
（你亲手做的蒙版、污点修复一律原样保留；只有那些**本来没有蒙版**的照片，程序才可能按风格的局部调整习惯新建局部调整。）

- 平台：**仅 Windows**（依赖 `win32com` 调 Photoshop、Windows 凭据管理器存密钥）
- Python：3.10+
- 输出：JPG（sRGB / Adobe RGB(1998) / Display P3，质量按 Photoshop 0–12 刻度可调）
- 模型：**不写死**。填 API key 后自动拉取**这条连接**真实可调的模型列表
  （内置 12 家预设：DeepSeek / OpenAI / 通义千问 / 智谱 GLM / Gemini / Kimi / OpenRouter /
  Groq / xAI / 豆包（火山方舟）/ 百度千帆 / Perplexity；中转站、内网网关、本地 Ollama
  也可以自己建一条连接，见「[配置模型](#配置模型)」）

## ⚠️ 三件必须先知道的事

### 1. 必须开启 Camera Raw 的侧车文件选项

> **Camera Raw 首选项 → 文件处理 → 勾选「将图像设置存储在侧车 .xmp 文件中」**

不勾选这一项，ACR 与 Photoshop 打开 RAW 时**不会读取**旁侧 XMP，
本程序写出的一切参数都不会生效——而程序本身不会报错，因为文件确实写成功了。
这是最常见的"为什么完全没效果"的原因，请优先检查。

在 Photoshop 里改：`编辑 → 首选项 → Camera Raw…`（或 Camera Raw 窗口内的齿轮图标）。
在 Bridge 里改：`编辑 → Camera Raw 首选项…`。

### 2. DNG 会直接改写你的原片，请先备份

DNG 的 XMP 嵌在文件内部，ACR 优先读取嵌入元数据，旁侧 `.xmp` 可能被忽略或冲突。
因此本程序对 `.dng` 采用「读出嵌入 XMP → 修改 → 写回文件内部」策略，
**不会**生成 `foo.dng.xmp`。

这**会直接修改你的 DNG 原片**。安全措施：
- 程序调用 exiftool 写回时**不加** `-overwrite_original`，
  因此 exiftool 会自动生成一份 `<原文件名>_original` 备份；
- 出问题时可把 `*_original` 改名回原名完整恢复；
- 写回命令带 `-m`（忽略**次要**错误）：某些 DNG（实测 DJI）的 maker notes
  无法解析，exiftool 会报 `Error: [minor] Maker notes could not be parsed`
  并**一个字节都不写**；带 `-m` 后才能正常写入（实测标签总数与像素数据长度均不变）；
- 写完之后程序会**把包读回来核对**本次写入的字段名，缺一个就按失败报
  —— exiftool 返回 0 不等于参数真的进去了。

万一某个 DNG 写不进去：日志（不只是界面状态栏）里会有 `写 XMP 失败` 的行，
批次末尾还会汇总一句，并且它**不会被算作完成**（汇总里的失败数含它）。

即便如此，**处理重要原片前请自行备份**。程序无法为你的数据负责。

### 3. AI 看的是缩略图，参数作用于 RAW，二者不可混用

程序从 RAW 中提取**相机内嵌的 JPEG 预览**（经 ICC 转换到 sRGB、长边缩至 1024），
交给 AI 判断。而 AI 输出的参数会作用于 **ACR 对原始 RAW 的中性渲染**。

两者的色彩并不相同：嵌入式预览带有相机机内风格（佳能 Picture Style、
富士胶片模拟等），是"相机当时加工过的结果"。程序会把这一点写进提示词，
提醒模型不要把机内风格当成"需要修正的偏差"。但你应该知道这个固有偏差的存在。

若你的机内风格与 ACR 渲染差异很大，请开启界面上的
**「高保真模式」**：跳过嵌入式预览，直接用 rawpy 解码（慢 1–5 秒/张，更接近中性观感）。

---

### 4. 横竖方向是逐张处理的（写蒙版时尤其关键）

相机拍竖构图时，RAW 里存的是**横向**像素 + 一个「旋转 90°」的标记。
ACR 的蒙版坐标按**未旋转的那一版（存储帧）**记录，而人看的、AI 说的是**显示帧**。

因此凡是涉及蒙版几何，都必须**逐张**读该照片的 EXIF 方向再换算 ——
同一批里可能既有 `Rotate 90 CW`、又有 `Rotate 270 CW`、还有横着的（实测 8 张样本里就有 3 种）。
本程序的做法：

* `acb/raw/orientation.py` 负责读方向与换算；**镜像类方向直接拒绝**（宁可报错，也不猜一个方向）；
* 写侧车时若**没有**提供照片方向，程序**直接报错**，不会按某个方向硬写蒙版；
* 全流程的几何一律用"显示帧"（你看到的方向）表达，写入前才换算成存储帧。

这条规矩来自一次真实事故：把 A 照片的蒙版坐标搬到方向不同的 B 照片上，
ACR 里蒙版整体转了 90°（本该盖住天空的椭圆跑到了画面下方 1/3 处）。

## 安装

```bat
:: 1. 建议先建虚拟环境（build.bat 会自动做这件事）
python -m venv .venv
.venv\Scripts\activate

:: 2. 安装依赖
python -m pip install -r requirements.txt
```

国内网络若太慢，可先换镜像源：

```bat
python -m pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

### 可选但强烈建议：安装 exiftool

exiftool 用于提取嵌入式预览与读写 DNG 内嵌 XMP。**没有它程序仍能工作**，
但会降级为 rawpy 全解码（每张慢 1–5 秒），且**无法处理 DNG**。

> 发布版（`dist\AutoColorDiffusion` 或桌面上的 zip）**已经整份捆绑了 exiftool**，
> 解压即用，不需要用户装任何东西；只有从**源码**运行开发时才需要自己准备（见下）。

开发机（源码运行）推荐方式：从 <https://exiftool.org> 下载 Windows 版，
解压到 `<项目根>\vendor\exiftool\`（启动器 `exiftool.exe` 与 `exiftool_files\` 必须在一起），
或设环境变量 `ACB_EXIFTOOL_DIR` 指向现成目录 —— 打包时会自动找到它。

或者加入 PATH：`winget install exiftool` / `choco install exiftool`，
验证：新开 PowerShell 执行 `exiftool -ver`。

**关于 ICC 文件**：**你不需要装任何东西，文件有或没有都一样** —— 但这**绝不等于"没做色彩管理"**：

- 输入侧的 ICC 转换是**一定执行**的（不是"有文件才做"）：按嵌入 profile / EXIF 判定源色空间
  → LittleCMS 转换到 sRGB → 输出 JPEG **必定嵌入 sRGB profile**。转换走的是
  `ImageCms.profileToProfile`，与"手上有没有那个 .icc 文件"无关。
- **Adobe RGB (1998) 需要的 profile 已经随程序分发了**：
  `assets/icc/AdobeRGB1998-compatible.icc` —— 由本程序按 Adobe 公开的色度参数
  （D65、gamma 563/256、三原色 xy）自己生成，描述写的是
  `Compatible with Adobe RGB (1998)`。这是 Adobe 官方**要求**的措辞（见
  「[许可与致谢](#许可与致谢)」的原文引用）：第三方不许把它叫做 "Adobe RGB (1998)"，
  但**允许**按规范自制等效 profile 并这样标注。
- 你机器上**真有 Adobe 官方那份**时（装了 Photoshop 一般就有），程序会优先用它；
  自带的等效文件不会抢占、不会覆盖官方文件。
- `DisplayP3.icc` 现在用不到：输出侧只把**配置文件名称**交给 Photoshop 的 `convertProfile`，
  用的是你本机那份。

细节与实测记录见「[输入侧的色彩管理](#输入侧的色彩管理不是可选项)」。

## 运行

### 图形界面

```bat
python app.py
```

界面遵循 Windows 11 的 Fluent 设计语言（冷静、柔和、整洁）：圆角卡片、强调色
`#0078D4`、支持浅色 / 深色切换；Windows 11 上还会尽力套上 Mica 云母背景
（旧系统自动退回纯色，不影响功能）。

主界面只有两栏：

- **左侧「照片」卡片**：添加照片 / 添加文件夹 / **移除选中** / 清空，照片列表，
  下面一条细进度条、一行环境自检小结，以及产品名与版本号。
- **右侧「调色助手」卡片**：像 AI 聊天框一样，把「工作模式（输出/训练）」、
  **连接**（端点 + 密钥 + 备注名）、模型、风格、提示词整合在一起；底部三行：
  行 1 是「☑ 输出 / 输出目录 / _export 子目录」，行 2 是「输出色彩空间 / 输出质量」，
  行 3 是「输出格式 / 尾缀」加运行按钮。
  **「输出」排在所有输出设置的最前面**：它决定的是"到底出不出片"，
  后面的位置/色彩空间/质量/格式/尾缀都是它的从属设置。
  勾上才会真的调用 Photoshop 导出；取消勾选就只写 XMP、不导图，
  **后面所有输出设置（含输出目录与 _export 子目录）一并变灰**。
  **「输出目录」与「输出到 _export 子目录」也在主界面上**（就在「输出」开关右侧）——
  它们曾经住在高级设置里，用户会以为程序不能自选输出位置。
  **连接与模型在两种模式下都在**（训练同样要调 AI），配一次就一直有效。

**移除选中**只把照片移出待处理列表，**不会删除或修改磁盘上的任何文件** ——
选错一张时不用重头再来。

### 整理风格 / 模型：右键列表里的条目

**在「风格」或「模型」下拉列表里，右键任意一条**，就可以：

| 菜单项 | 风格 | 模型 |
|---|---|---|
| **置顶 / 取消置顶** | 排到列表最前面 | 同左 |
| **删除** | 真的删掉 `styles/<名字>.json`（会弹窗确认） | 仅**从下拉移除**，`models.yaml` 不动 |

- **置顶的条目有标识**：前面带 `★` 且**加粗**（两项一起用是故意的 ——
  万一某个字体缺 `★` 字形，加粗仍然能让你看出哪几条是置顶的）。
- 右键后**选项列表会保持展开**，菜单盖在它旁边：选「置顶」能当场看到那一项
  重排到最前并多出 `★`；选「删除」能当场看到它从列表里消失。
  （下拉本身在"选中条目上松开鼠标"时会自己收起来 —— 右键也一样，那是 Qt 的行为。
  所以右键的按下/松开会被事件过滤器拦下，否则菜单还没出来列表就没了。）
- 置顶项会排在列表最前面，选中的那一项**不会因为置顶而丢失**。
- 下拉第一项「（不选，使用内置默认策略）」是占位项，右键时只给一句灰掉的说明。
- 模型删除后随时可以用「高级设置 → 恢复出厂设置」找回（会一并把连接、密钥、失败记录、
  缓存与界面偏好重置，所以会弹两次确认）。
- 程序自带的风格会被种子自动补齐，所以**拒绝删除**并说明原因。

> 为什么用右键而不是常驻按钮：置顶/删除是偶尔用一次的整理动作，
> 常驻按钮会挤掉下拉的宽度，而且它们只能作用在「当前选中项」上 ——
> 得先选对再去点，很容易作用到隔壁那一项。右键直接作用在**你正指着的那一条**上。
>
> 实现上用的是**事件过滤器**而不是 `customContextMenuRequested` 信号：
> 走信号那条路时 Qt 会先把右键事件走完它自己的弹窗处理（下拉本身是 `Qt::Popup`，
> 带着 grab），紧接着再弹一个菜单就会和它撞上，实测直接报
> **0xC0000005 访问冲突**（进程被系统直接终止，日志里一行都留不下）。
> 所以现在一律 `return True` 把右键事件吃掉，让 Qt 的默认处理不发生，
> 再用单次定时器把菜单推迟到下一轮事件循环里弹。
> 这类崩溃**进程内测试抓不住**，回归守卫是子进程跑 `tools/menu_crash_probe.py`
> （发真实 `QContextMenuEvent`，看退出码）。
>
> **同一个家族后来又踩了一次**：右键菜单装到**第三个**下拉（「连接」）之后，崩溃换了形态回来 ——
> `tools/menu_crash_probe.py open` 在 8 次里有 **3 次**以 `0xC0000005` 结束，
> 而且发生在**窗口关闭之后的进程收尾阶段**（stdout 里 `PROBE_OK` 都打完了）。
> 根因：事件过滤器是以 combo 为 C++ 父对象的 QObject —— 窗口销毁时 C++ 侧先删掉它，
> Python 侧还持有引用，收尾阶段碰到已销毁的包装就是访问冲突。
> 现在 `closeEvent` 会先把过滤器逐一 `removeEventFilter` + `setParent(None)`
> （`_detach_menu_filters()`），加上这段之后复测 **20/20 次干净**。
> 探针也因此加了 `all` 变体：**这类崩溃与"装了几个过滤器"有关，只测一个下拉是看不见的**。

日常用不到的东西收进了左上角菜单栏（类似 PS 的「首选项」）：

| 菜单 | 内容 |
|---|---|
| **文件** | 打开输出目录、**打开风格文件夹** |
| **外观** | 浅色模式 / 深色模式（无缝切换，选择会被记住） |
| **安全** | 删除已保存的密钥…（列出所有存了密钥的连接，每条删前确认） |
| **高级设置** | 打开高级设置（并发数、最大请求数、缩略图缓存、高保真、DNG 旁侧、**离线调试**）、恢复出厂设置…、重新自检 |
| **日志** | 查看运行日志（弹窗）、打开日志目录、清除失败记录、清除缩略图缓存 |
| **帮助** | 关于（作者 / Bilibili / rednote / Github / afdian 与版本号，链接可点） |

> 分组按"这件事是关于什么的"来分：**凭据相关的动作单独进「安全」**，
> **排障会用到的一整组进「日志」** —— 之前把"打开输出目录"和"删除密钥"塞进同一个「工具」里，
> 危险动作与日常动作混在一起（用户 2026-09-24 指出）。
>
> **「打开脚本目录」不在菜单里**：它只对"自动导出失败、需要手动补跑"这一个场景有意义，
> 而那个场景下**完成对话框里会当场给出按钮**（`manifest.json` / `export_batch.jsx` / `run_export.bat` 都在那儿）。
>
> **「恢复出厂设置」会弹两次确认**（用户 2026-09-24 要求「警示 + 二次确认」）：
> 第一次按**真实状态**逐条列出"会重置什么"——
> 连接列表（删掉自定义连接文件，回到出厂那几条）、
> **已保存的 API 密钥（直接删除、无法恢复，之后要重新粘贴）**、
> 被移除（隐藏）的模型（全部放回下拉）、
> 界面偏好（主题 / 置顶 / 尾缀 / 格式 / 色彩空间 / 质量 / 上次选用的模型与风格）、
> **失败记录（含「永久跳过」档案，清掉后这些文件会重新入队）**、
> **缩略图缓存（下次运行重新提取，更慢但结果不变）**；
> 并明确"**绝不动什么**"：`styles/` 里训练出来的风格文件、你的照片与 XMP 旁侧文件、`models.yaml`。
> 第二次才是真正的"确认重置"（不能撤销）。两个框的默认按钮都是**取消**，直接回车不会误放行。
>
> ⚠ 密钥是由**连接文件里的账户名**定位的（自建连接的账户名是 `conn:<备注名>`），
> 所以删除顺序是"先删密钥、再删连接文件" —— 反过来的话那些账户名就再也枚举不出来，
> 密钥会永久留在凭据管理器里而用户以为已经清掉了。
> 环境变量里的同名密钥**程序无权删除**，会单独列出来如实告知。
>
> **没有「打开配置文件夹」入口**，这是刻意的：那里面是 `models.yaml`，
> 一旦被误开、顺手改坏，下次启动就会报「模型配置」错误。
> 真需要改的时候，路径在**模型下拉的悬停提示**里写着：
> `%APPDATA%\AutoColorDiffusion\config\models.yaml`（便携模式则是 `<exe目录>\data\config\models.yaml`）。
> 风格目录日常会用到（看一眼 / 备份），所以保留了「打开风格文件夹」。

**「开始」与「续跑」的区别（容易搞混，特意说明）**：

| 按钮 | 行为 |
|---|---|
| **开始** | **全量重跑**：已完成的文件也会重新请求 API。改了提示词想重来一遍就用它。 |
| **续跑** | 跳过已完成的文件（不重复请求 API），只补跑缺的。 |
| **只跑失败** | 只处理上次失败过、且没到永久跳过阈值的文件。 |

运行模式会写在日志第一行（「全量：已完成的文件也会重新请求 API」或
「续跑：跳过已完成的文件」），不确定时看一眼日志即可。

> ⚠️ **全量重跑不会覆盖已有的出图**：文件名按尾缀规则递增（见下节），
> 这是为了防止误覆盖你的成品。所以反复重跑会**累积**输出文件。
> XMP 侧则是原位覆盖（读-改-写，不动蒙版）。

### 离线调试（原「离线模拟」+「演练模式」合并）

高级设置里只有一个勾选框：**「离线调试：不调用 AI、只处理前 3 张，用写死的假结果验证链路」**。

| 旧版只勾了其中一个 | 后果 |
|---|---|
| 只勾「离线模拟」 | 不烧钱，但 100 张全跑，写满一堆假参数 |
| 只勾「演练模式」 | 只跑前 3 张，但**真的在调 API**，每一步都在花钱 |

它们本来就是同一件事的两半 ——「在不烧钱、不碰整批照片的前提下把链路走通」，
所以合并成一个开关。勾上之后同时生效：

- **不联网、不需要密钥**：走离线适配器，注入一份写死的、结构完整的假分析结果
  （训练模式同样可用，返回写死的假风格画像）；
- **只处理前 3 张**，出片落到 `<源目录>/_export_dryrun/`，与正式产物**绝不混放**；
- **仍然会写 XMP**（保留这条写链路的验证路径），但里面全是假数据，**别用于交付**；
  日志与每条结果的说明里都会标注 `[离线调试]`。想连 XMP 都不写：命令行加 `--dry-run-no-xmp`；
- **「连接 / 模型 / 密钥」整组变灰停用**：它们对离线结果没有任何影响，
  留着能点只会让人以为"选的模型会起作用"（"看起来能用但实际被忽略"是吃过亏的老问题）。
  密钥状态那一行会写明为什么变灰。

它验证的是**除 AI 之外的一切**：预览提取 → 结果校验 → XMP 读-改-写 → 导出命名去重 →
`manifest.json` / `export_batch.jsx` / `run_export.bat` 生成。命令行等价写法：

```bat
python app.py --no-gui --files D:\photos --mock-ai --dry-run --no-photoshop
```

> **假结果也要过真校验**：那份写死的数据会先经过生产代码用的同一个 `xmp.validator`，
> 所以"能跑通"确实等价于"结构与校验链路是对的" —— 写错字段名或取值越界会立刻报错，
> 而不是被一个"假通过"的链路掩盖。

#### 内置「AI自主决策」（`AI自主决策.json`）：不预设偏好，让模型按图判断

风格下拉里有一个**软件内置**的选项 —— 「AI自主决策」。它的含义是**不放任何个人偏好进去**：
由模型按每张照片本身判断该往哪调、调多少（影调、HSL 分区、颜色分级、分离色调、相机校准都可以用）。
适用场景：你还没训练风格、想先看看"没有任何偏好约束时模型会怎么调"，或者这一批照片题材太杂、
不想被单一风格统一。

它与「内置基准风格」有两点区别，别混：

| | `default_neutral`（内置基准） | `AI自主决策`（内置自主决策） |
|---|---|---|
| 能不能选 | **只在勾选「离线调试」时可选**（日常请选「（不选，使用内置默认策略）」，效果一样） | **任何时候都能选** —— 它是给日常用的功能 |
| 干什么 | 保守的批内一致性校正（改动幅度都有上限） | 不设审美方向，让模型自己决定 |
| 能不能删 | ❌ 删了下次启动也会被补回来 | ❌ 同上 |

> ⚠ **「不做限制」只针对审美方向，程序侧的硬规则一条都不放宽。** 选它的时候，
> 下面这些照样生效，而且**对任何风格都一样**（内置的、你训练的、手写的）：
> 只能用已登记的 `crs:` 字段、不许返回机器/版本字段与相机配置、取值必须在表定范围内、
> 只返回需要改动的字段、响应结构由 schema 约束、越界由本地强校验拒收并重试。
> 这些规则写在系统提示词与 `xmp/fields.py`、`xmp/validator.py` 里，与选哪个风格无关 ——
> 自检里有一条断言专门盯着这件事（对三种风格各跑一遍"机器字段/相机配置/未登记字段/越界值"，
> 必须全部被拒）。

#### 内置基准风格（`default_neutral`）只在离线调试下可选

`styles/default_neutral.json` 是程序自带的中性基准风格，不是训练出来的风格：

- **界面里删不掉**（删了下次启动也会被 `ensure_seed_styles()` 补回来，所以干脆不提供删除）；
- **只在勾选「离线调试」时可选**，平时在下拉里是**灰的**；
- 日常使用请选「（不选，使用内置默认策略）」——效果完全一样，而且不会被误当成训练成果；
- 如果它恰好是"上次选中的风格"，关掉离线调试时会被自动弹回「不选」
  （灰掉却仍然生效，比不能选更糟）。

### 导出格式与文件名尾缀

右侧底栏的「格式」与「尾缀」两个控件控制出片长什么样：

| 格式 | 扩展名 | 说明 |
|---|---|---|
| **JPG** | `.jpg` | 体积最小、最通用；画质由右边的滑块决定（Photoshop 0–12 刻度） |
| **PNG** | `.png` | 无损，适合截图/网页素材；画质滑块自动置灰 |

> ### 为什么没有 TIFF
>
> TIFF 能不能脚本化导出，取决于 Photoshop 的脚本 DOM 里有没有
> `TIFFSaveOptions` 这个对象。**实测 Photoshop 2026（27.0.0）已经没有它了**
> （同一版本里 `JPEGSaveOptions` / `PNGSaveOptions` 都还在），
> 因此无法通过脚本导出 TIFF。两条替代路线也都被排除：
>
> - `doc.saveAs(文件)` 不带格式参数时，Photoshop 会按**默认格式存成 PSD**，
>   扩展名根本不决定格式（实测把 `.tif` 写成了 `.PSD`）；
> - 改用 ActionManager（`executeAction('save', As=TIFF)`）会弹出
>   「TIFF 选项」模态框并**挂死**——那比报错严重得多（整批卡住，
>   Photoshop 停在弹窗上等人点）。
>
> 与其提供一个"选中后必然失败"的下拉项，不如**不提供**。
> 需要 TIFF 的话：先用本程序导出 JPG，再在 Photoshop 里手动「另存为 TIFF」。

> 小提示：Photoshop 保存时会把扩展名**规范成大写**（`.JPG` / `.PNG`）。
> Windows 文件系统不区分大小写，所以不影响冲突检测与使用，只是名字看起来是大写的。

**文件名尾缀**：导出文件名 = 原主文件名 + 尾缀 + 扩展名。

| 你填的 | 第一次导出 | 已有同名时 |
|---|---|---|
| *（留空）* | `IMG_001-1.jpg` | `-2.jpg`、`-3.jpg` …… **数字递增** |
| `edit` | `IMG_001-edit.jpg` | `-edit_2.jpg`、`-edit_3.jpg` …… **尾缀后追加** |
| `_v2` | `IMG_001_v2.jpg` | `-v2_2` 不会出现；统一追加 `_2` |

两个细节值得说明（都是用户明确要求）：

- **绝不叠成 `-edit-edit`**：如果源文件主名已经以该尾缀结尾，程序会先剥掉再追加。
- **默认尾缀不会写成 `-1_1`**：留空时用的是“第几次导出”语义，
  所以冲突时直接把数字换掉（`-1` → `-2`），而不是在 `-1` 后面再接 `_2`。

尾缀框里填的内容会**即时存盘**，下次打开程序自动带出（见下节的 `preferences.json`）。
文件名里的非法字符（`\ / : * ? " < > |`）会被自动剔除，标签上会立刻显示实际会用的尾缀。

#### 哪些选项会被记住

下面这 6 项都是**改完即存**，关掉程序再打开会自动带出上次的选择：

| 选项 | 带不出来的情况 |
|---|---|
| 输出色彩空间 | 选项从程序里消失了（回退到第一个，并记一条日志） |
| 格式（JPG / PNG） | 该格式已不再提供（如旧的 TIFF，会回退到 JPG 并说明原因） |
| 输出质量 | 值超出 0–12 时**夹紧**到边界 |
| 文件名尾缀 | — |
| 风格 | 那个风格文件被删了 → 回到「不选，使用内置默认策略」 |
| 模型 | 该条目被隐藏或从 `models.yaml` 里删了 → 回到配置里的 `active` |

存在 `preferences.json` 里，与源照片、XMP 无关，换一台机器不会跟着走
（想跟着走就用便携模式，或直接拷这个文件）。

### 输出到哪里（出片目录 vs 脚本目录）

这两件事以前混在一起，现在**彻底分开**了：

| 类别 | 落在哪 | 关闭程序时 |
|---|---|---|
| **出片 JPG** | **与源 RAW 同目录**（默认），即 `D:\photos\x_E.jpg` | 保留，这是你的成品 |
| **脚本三件套**<br>`manifest.json` / `export_batch.jsx` / `run_export.bat` | `<数据目录>\runs\<运行标识>\` | **整个目录删掉** |

**为什么脚本不放在出片目录里**（这是一个真实反馈）：出片目录是你要交付出去的
目录，只该有 JPG。那三个文件是驱动导出的"机器件"，留在里面既碍事、
又会在打包交付时被一起发出去。它们的生命周期也短得多 —— 导出跑完就没用了。

完整规则：

| 场景 | 出片目录 |
|---|---|
| 默认 | 与源 RAW 同目录（同层） |
| 勾了「输出到 _export 子目录」 | `<源目录>/_export/` |
| 填了「输出目录」框 | 以填写为准（填了就用它，离线调试也一样） |
| **离线调试** | `<源目录>/_export_dryrun/`，与正式产物**绝不混放** |

> 「输出目录」框与「输出到 _export 子目录」都在**主界面**底栏第一行（「输出」开关右侧），
> 不在「高级设置」里；勾了子目录后输入框会置灰，且它的值会被忽略（两者不会互相覆盖）。

> ⚠️ **需要手动补跑导出时，请在关闭程序之前做**。
> 脚本目录在退出时会被自动清理，`run_export.bat` 自然也一起没了。
> 程序会把这种情况识别出来并**保留**那一次（完成对话框里会直接给「打开脚本目录」按钮），
> 但要长期留着（例如准备拿到另一台机器上跑），请当场把整个目录复制到别处。
>
> 命令行模式同理：跑完会清掉运行目录，只有"Photoshop 没成功"时才保留并打印出路径。

### API 密钥

密钥**绝不写入任何配置文件或代码**。程序按以下优先级读取：

1. 本次会话内存（你在界面上刚输入的）；
2. Windows 凭据管理器（`keyring`，服务名 `AutoColorDiffusion`，账户名 = 这条连接的 `key_env`：
   出厂连接沿用 `DEEPSEEK_API_KEY` 这类旧名，自建连接是 `conn:<你起的名字>`）；
3. 同名环境变量（便于 CI / 无人值守）。

界面上的密钥输入框仅在密钥链中**无值**时才需要填写，回填时以掩码显示 `sk-****xxxx`。
密钥链不可用时程序会给出安装指引，并只在内存中保存（重启需重输）——
不会退化成"自己实现一套加密写进文件"。

**粘贴的密钥会被清理后保存**（实测真实常见）：

- 去掉首尾空白（含全角空格、换行、零宽字符）；
- 去掉包裹的引号（`"…"` / `'…'` / `` `…` `` / `「…」` / 中文引号）；
- 去掉多余的 `Bearer ` 前缀。

而下面两种形状会**直接拦下来让你重拷**（它们不可能是密钥，一定是复制错了）：

- 含全角字符（会报出“第 N 个字符是「ａ」（全角/非 ASCII，U+FF41）”）；
- 中间有空格或换行（常见于把两行一起复制了）。

> 为什么要拦而不猜：带着一个全角字符发出去，服务端只会回 401，
> 而你会去查余额、权限、模型名 —— 真正的原因在自己复制的那串字符里。

**“存在哪里”会说真话**：密钥链可用时状态栏写“已保存到系统密钥链”；
不可用时写“⚠ 只在**本次会话**有效，关闭程序后需重输”（橙色），
绝不会把“只存在内存里”说成“已保存”。

#### 密钥安全性到底如何（如实说明）

**能防住的**：

- **不会明文落在任何文件里**。持久化走 Windows 凭据管理器
  （`keyring.backends.Windows.WinVaultKeyring`），底层由 **DPAPI 按当前用户加密**，
  存储位置在 `%LOCALAPPDATA%\Microsoft\Credentials\`，不是文本文件。
- **不会进日志**。所有打印密钥的地方都过 `mask()`（`sk-****xxxx`）；
  请求只在 `Authorization: Bearer` 头里带上它，绝不放进 URL——
  并且代码**显式把 `urllib3` / `requests` 的日志级别压到 WARNING**，
  因为这两个库在 DEBUG 下会把请求头（含密钥）写进日志文件。
  这条在 `logging_setup.py` 里有注释说明，不是碰巧。
- **同一台机器的其他 Windows 用户读不到**（DPAPI 的密钥派生自当前用户的登录凭据）。
- **界面输入框默认掩码**（`EchoMode.Password`），需要点「显示」才明文。

**防不住的（务必知道）**：

- **以你的身份运行的恶意程序可以读到它**。凭据管理器没有"只允许本程序访问"的能力，
  同用户下的任何进程都能调用 `CredRead` 取走。这是 Windows 凭据管理器的固有边界，
  不是本程序的实现缺陷——**任何**把密钥存在本地的程序都是这样。
- **你自己把密钥贴进 `models.yaml` 或脚本里**（那样就绕过了整套机制）。
  程序不会这么做，但它拦不住你手工这么做。
- 环境变量方式（优先级最低的兜底）对同用户进程同样可见。

**想更安全的话**：

- 用**受限额度的子密钥**，别用主账号密钥；
- 用中转站时给它单独发一把 key，泄露了可以随时吊销；
- 真要彻底隔离，就给这把 key 设好消费上限——本地存储的密钥，
  本质上防的是"别的用户/明文文件被拷走"，防不了"你的账户被攻陷"。


#### 删除已保存的密钥（二次确认）

密钥存在 Windows 凭据管理器里，你可以随时删掉它。两个入口，**都会先弹确认框**：

- 密钥输入框右边的 **「删除」** —— 删除**当前连接**的密钥；
- 菜单 **安全 →「删除已保存的密钥…」** —— 列出所有**已保存了密钥**的连接让你挑一条
  （12 条出厂连接各有独立密钥槽，逐个切连接点删除既慢又容易删错账户）。

确认框里会写清：账户名、当前值的掩码、**这把密钥现在从哪来**（本次会话内存 / 系统密钥链 /
环境变量），以及删除后会发生什么。**默认按钮是「否」** —— 删除不可撤销，手快连按两次回车
不该把密钥删掉。

删除会做什么、不会做什么：

| | 说明 |
|---|---|
| ✅ 清掉本次会话内存里的副本 | 删完立刻不再使用它（不用重启） |
| ✅ 移除凭据管理器里的条目 | 不可撤销；要恢复只能重新粘贴一次密钥 |
| ❌ **删不掉环境变量** | 环境变量是你在系统里设的，程序无权修改。若同名环境变量仍存在，程序会继续读它 —— 这时界面会**明确告诉你**"仍在由环境变量提供，要彻底停用请去删那个环境变量"，而不是假装删干净了 |
| ❌ 不影响照片、风格、模型与其它设置 | 只动密钥本身 |

> 这一条与早先的"密钥复用提醒"是同一类纪律：**界面上的每句话都要与真实状态一致**。
> "我执行了删除"不等于"密钥已经不存在了"，程序必须把两者的差别说出来。
### 命令行（无界面）

```bat
:: 演练：只跑 3 张，验证链路
python app.py --no-gui --files D:\photos --dry-run

:: 离线调试（界面上的勾选框）：不联网、不需要密钥，用写死的假结果把整条链路跑通
python app.py --no-gui --files D:\photos --mock-ai --dry-run

:: 正式跑一批
python app.py --no-gui --files D:\photos --prompt "海边日落，保留暖调，肤色别过饱和"

:: 续跑（跳过已完成的，不重复请求 API）
python app.py --no-gui --files D:\photos --resume

:: 不带 --resume 就是全量重跑：已完成的文件也会重新请求 API（默认行为）

:: 只重跑失败过的
python app.py --no-gui --files D:\photos --only-failed

:: 清除失败记录（含永久跳过标记）后退出
python app.py --clear-failures

:: 训练模式：从 (RAW + XMP) 对归纳风格
```

| `--model` | 指定用哪个模型，格式 `连接id::模型id`（例如 `--model deepseek::deepseek-flash`）；可用值见界面「模型」下拉的悬停提示 | 第一条连接的第一个模型 |

#### 关于输出质量刻度

质量值直接使用 **Photoshop 自己的 0–12 刻度**（0 最低、12 最高）。界面滑块与
`--quality` 用的是同一个值，中间**没有任何换算**：你选 11，`manifest.json` 里就是 11，
Photoshop 收到的也是 11。

- **12 是 Photoshop 的上限**，约等于 libjpeg 97。真实的 libjpeg q100（几乎不做量化）
  在 Photoshop 里无法表达，这是本工具的出片画质天花板。
- 早期版本用的是「低/中/高/最高」四档 + 一张换算表，**已废弃**：Photoshop 只有 13 档，
  四档映射进去会出现两档产出**完全相同**的文件，而且「最高」档声称的 q100 根本做不到。
  为兼容你已经写好的脚本，`--quality 高` 这类旧写法仍可用，程序会转换并打印提示。
- 质量 ≤ 3 属于「极限压缩」区间（0 约等于 libjpeg 5），压缩伪影肉眼可见。
  界面会在滑块旁**标红并显示 ⚠ 极低画质**，点「开始」时还会弹一次确认框；
  命令行则只打印 `[警告]`（无人值守场景弹框会直接挂死，所以不拦截）。
  这个阈值定义在 `acb/constants.py` 的 `PS_JPEG_QUALITY_WARN_MAX`，想只警告 0 就改成 0。

#### 关于请求超时与重试

| 项 | 当前值 | 定义位置 |
|---|---|---|
| 单请求超时 | **看图连接都是 180 秒**（不看图的 Perplexity 仍 60） | `config/models.yaml` / `config/connections.yaml` |
| 超时后的重试 | 把读超时**翻倍**（180 → 360，天花板 600） | `constants.TIMEOUT_ESCALATION_*` |
| 常量里的兜底超时 | 5 秒 | `constants.REQUEST_TIMEOUT_S` |
| 连接超时 | 5 秒 | 必须 ≤ 总超时，否则"总超时"是句空话 |
| 失败后重试 | **1 次**（共 2 次尝试） | `constants.MAX_PARSE_RETRIES` |
| 同文件永久跳过 | 累计失败 2 次 | 与重试次数**必须对齐**，否则会出现"重试还有名额但文件已被永久跳过" |
| 单批请求上限 | 文件数 × 2 | 同上对齐 |

**为什么是 180 而不是 60**（2026-09-24 真实报错复盘）：
用户用 GLM（`glm-5.3-flash`）跑一批，报了一屏「请求超时」，日志里写的是
`read timeout=60`。实测下来两件事：

1. 端点本身很快（`/models` 0.15 秒、纯文本对话 0.9 秒）——不是网络问题；
2. 那个模型是**强制思考**的（官方《思考模式》明文：`GLM-5.3` / `GLM-5.3-FLASH`
   不支持关闭思考），一次带图请求实测要 **51 秒**；4 张并发时总有一批刚好越过 60 秒。

所以现在：**凡会带图的连接一律 180 秒**（厂里 11 家已统一），并且**超时后的那次重试
会把读超时翻倍**（不是重发一个同样的 60 秒请求）。
两条都必要：只靠“翻倍重试”虽然也能成，但会白花一次请求，
而单批预算只有「文件数 × 2」——每张都白花一次的话，后面的照片会被预算卡住。

> **升级注意**：老配置里那个 60 秒（以及几个写小的 `max_output_tokens`）会在程序启动时
> **自动修成新值**（`acb/config.py` 的 `CAPABILITY_FIXES`，判据是“你的值恰好等于
> 我们当年写的值”）。你自己手改过的值不会被覆盖。

视觉模型处理 1MP 图并输出结构化 JSON 的 P95 延迟通常在 10–30 秒，
但**开了思考模式的模型**（GLM 5.3 系、DeepSeek 默认、豆包深度思考…）会明显更慢且无法关。

> **常量里那个 5 秒只是兜底**，不会用在真实调用上：`ModelSpec.request_timeout_s`
> 优先于常量（预设与自建连接都会把值写进 `ModelSpec`）。
> 想给某条连接单独调（例如内网网关很慢），改它那条的 `request_timeout_s` 即可，不用动代码。
>
> 自检里有一项专门守着"重试次数 ↔ 永久跳过阈值 ↔ 预算倍数"的对齐关系，只改一个会失败。

#### 关于限流：并发数与每分钟请求数（账户级）

有些家的限流是**按账户**给的，跟你的机器、并发设置无关。两种都要接住：

> **默认并发已从 4 降到 2**（用户 2026-09-24 实测）：带图请求每张要上万 token，
> 并发 4 时 qwen/DashScope 会撞 TPM 限流（18:08 那轮 15 张 429）、GLM 这种思考模型则频繁读超时
> （它单发实测就要 51 秒）。降并发不会让代码变快，但能让「跑完有一两张红」消失——
> 而失败→重试→拆单重发不只慢，还多花钱。要冲量可以自己调大（1–16）。
>
> **另外程序会自己降档**：一旦收到 429 限流或读超时，**本轮运行**的端点并发上限自动减半
> （1–16 都能降：4→2→1，下限 1）。只降不升、**不写记忆**，而且**下一轮开始时会重置回基准**
> （否则同一会话里连着跑几轮会“越跑越慢”）。日志会写明降到了几。
> 依据：他试了一整天并发数，结论是手动来回试不如程序自适应。

| 项 | 说明 |
|---|---|
| `max_concurrency` | 同时最多几个请求在飞。超过了服务端就直接 429，**不排队** |
| `max_rpm` | 每分钟最多发几次请求 |
| 出厂默认 | 写在 `config/models.yaml` 对应服务商下（当前只有 Kimi 写了）。**出厂按 Tier1：并发 15 / RPM 100** —— 依据见表下方 |
| 界面一键切换 | 切到 Kimi 时，模型下拉下面那行红字里有一个可点的链接：未充值的账户点一下即改为 Tier0（并发 1 / RPM 3），已充值的用户看到的是「点此改回 Tier1」。**这个选择写在 `<数据目录>\config\connections.yaml` 的连接条目里**（连接优先于 `models.yaml`，所以手改 `models.yaml` 不影响它） |
| 自动学习 | 429 原文里写了数字（如 `max organization concurrency: 1` / `max org RPM: 3`）时，程序会读出来、写进 `<数据目录>/state/endpoint_capabilities.json`，日志里告知；**只能收紧，不会放宽** |
| 冷却 | 429 之后全端点一起等（优先用标准的 `Retry-After` 头），不是只让报错的那个请求等 |
| 适用范围 | **只作用于该端点**（base_url）。换回别的连接不受影响，不存在"被 Kimi 限制连累" |
| 想改回来 | 界面上点那行红字里的链接即可（两个方向都能切）；想清掉学到的记忆就删那个 json 文件 |

真实例子（2026-09-24）：Kimi 官方《充值与限速》按**累计充值额**分档 ——
**Tier0（¥0）并发 1 / RPM 3；Tier1（¥50）并发 15 / RPM 100**，再往上更高
（代金券余额**不计入**累计充值）。用户用 4 个工人并发跑 Tier0 账户 →
18 张里只有 1 张成功，其余全是 429（默认并发现已降到 2，且限流后会自动再降档）。

> **程序无法替你判断档位**：官方没有查档位的接口 —— 实测 `GET /v1/users/me/balance`
> 只返回三个余额字段，对话响应里也没有任何 ratelimit 头。所以出厂按 Tier1 跑
> （否则充过钱的用户享受不到应得的并发），未充值的用户在界面上点一下即可切到 Tier0，
> 不必先自己撞几次 429 才知道。

> ⚠ 程序会用 `workers`（你设的并发）与这两个限制**取更严的一个**；
> 设 8 个工人在 Kimi Tier0 上也不会变快，只是多几个人排队。

**429 有两种，处理方式完全不同**（2026-09-24 用户真实碰到第二类，7 张失败）：

| 类型 | 怎么认（只看服务端原文） | 程序动作 | 你该做什么 |
|---|---|---|---|
| **调用频率限流**（RPS/RPM） | 原文里写 `rate limit` / `concurrency` / `RPM` | 读出并记住并发与每分钟次数（只收紧）、全端点冷却、退避重试一次 | 可以什么都不做：程序会自动变慢；想更快就降并发或升级套餐 |
| **账户配额/额度**（TPS/TPM、免费额度、账单、预算上限） | 原文里写 `quota` / `billing` / `plan` / `Arrearage` / 免费额度 | **不再重试**（等 1 秒没用），且**不**把它学成「并发 1」；失败也不计入「永久跳过」 | ① 等 1–5 分钟后点「只跑失败」；② 若每回跑到几十张就复发 = 每分钟 token 配额（TPM）被打满 → 把并发工人数降到 2 或 1；③ 连单张都失败才是额度/账单问题 → 去控制台查免费额度 / 计费与套餐 / 预算上限 |

依据：阿里云百炼《错误码》（2026-09-22 版）把 `429-Throttling.RateQuota/LimitRequests`
与 `429-Throttling.AllocationQuota/insufficient_quota` 分成两个条目，后者（配额/额度/账单）
**重试无效**。实测碰到的那条原文是
`You exceeded your current quota, please check your plan and billing details.`。
识别**只看服务端原文**、不靠状态码猜，所以 Kimi 那种
`request reached max organization concurrency: 1` 依旧走限流通道（重试 + 学习）。

> 顺带一条纪律：多图一份请求失败时，程序会「拆成单图再试一次」以隔离个别坏图 ——
> 但**配额类不拆**（配额与请求大小无关，拆完还是全失败，只会把一次失败变成 N 次请求），
> 同时**每张图仍然各产生一条失败结果**，不会让同组里没被上报的图静默消失。

> 还有一条：**账户级失败（额度/计费/密钥）不计入「失败 2 次即永久跳过」**。
> 否则会出现一个很难发现的陷阱 —— 你只是因为额度用尽失败了两轮，这几个文件就被
> 永久跳过；等你充完值再跑，它们仍然不处理（还得再点一次「清除失败记录」）。
> 现在它们只记「失败」不记「永久跳过」，充值或改完配置后直接重跑、
> 或点「只跑失败」就能捞回来；日志里也会写明「这次失败是账户侧的问题」。

## 工作流程

### 输出模式

```
1. 添加照片        白名单后缀（大小写不敏感，递归子目录）：
                   .cr3 .cr2 .nef .nrw .arw .srf .sr2 .raf .orf .rw2 .pef .dng
2. 提取嵌入式预览  exiftool -PreviewImage → -JpgFromRaw → -ThumbnailImage → rawpy 全解码兜底
                   （DNG：先 -JpgFromRaw，再用**带 8 MB 体积上限**的 -PreviewImage）
3. 转 sRGB 缩略图  ICC 转换到 sRGB → 长边 1024 → q85 JPEG → 嵌入 sRGB profile
                   缓存于 cache/thumbs/，键 = 大小|mtime_ns|文件名 的哈希
4. AI 分析         用户风格 + 本批提示词 + 批内统计中位数 → 每张图的 ACR 参数（JSON）
                   （提示词优先级见「提示词与风格」：**选了风格时不会再拿"不做 HSL"的保守提示词去盖它**）
5. 写 XMP          非 DNG → 同名同目录的 .xmp（读-改-写）
                   DNG     → 写回文件内部（读-改-写，自动生成 _original 备份）
                   **新建** XMP 时会按相机机内设置写入 crs:CameraProfile（见「相机配置」）
6. 生成并执行脚本  export_batch.jsx + manifest.json + run_export.bat
                   （**写在 <数据目录>\runs\<运行标识>\，不进出片目录**）
                   → 通过 win32com 调用 Photoshop 批量导出为
                     <主文件名><尾缀>.jpg / .png
                     （默认与源 RAW 同目录，见「输出到哪里」）
```

### 输入侧的色彩管理（不是可选项）

缩略图链路的每一环都是必须的，ICC 转换**不是"有文件才做"**：

```
解码 → EXIF 方向校正 → ICC 转换到 sRGB（LittleCMS，感知意图）→ 长边缩至 1024 → q85 JPEG + 嵌入 sRGB profile
```

**源色彩空间怎么判定**（`acb/raw/icc.py::_source_profile`，判定依据会写进日志）：

| 优先级 | 判据 | 结果 |
|---|---|---|
| 1 | 图片自带的 ICC 块 | 直接用它（最权威，相机预览大多带） |
| 2 | EXIF `ColorSpace=1` | sRGB |
| 3 | EXIF `InteropIndex=R03` | Adobe RGB (1998) |
| 4 | 以上都没有 | 按 sRGB 解释（硬约束 #2 规定的默认假设） |

**sRGB 那一侧永远拿得到**：优先用磁盘上的 `sRGB.icc`（`assets/icc/` 或系统色彩目录），
都没有就用 LittleCMS 的内置公开定义 `createProfile("sRGB")` 当场构造。
实测这两者**只在 ICC 头里的"创建时间"那 4 个字节上不同**（偏移 32..35 = 分/秒），
其余 584 字节逐字节相同、同一批颜色的转换结果完全一致（8 个颜色逐一比对），
所以"文件在不在"不影响正确性，只影响要不要构造一次。

**Adobe RGB (1998) 那一侧自带一份等效 profile**（`assets/icc/AdobeRGB1998-compatible.icc`），
所以"没装 Photoshop / 系统里没有那份文件"的机器也能正确转换。搜索顺序是
**"哪一份"优先于"放在哪"**：

| 优先级 | 名字（在每个搜索目录里依次尝试） | 说明 |
|---|---|---|
| 1 | `AdobeRGB1998.icc` / `.icm` / `Adobe RGB (1998).icc` / `.icm` | **Adobe 官方那份**，用户机器上真有就用它 |
| 2 | `AdobeRGB1998-compatible.icc` | 程序自带的等效文件（按公开参数生成） |

搜索目录：`assets/icc/` → `<数据目录>\assets\icc`（运行时自愈生成的位置）→
`%WINDIR%\System32\spool\drivers\color` → Adobe 的公共/本地色彩目录。

> ⚠️ **实测记录（别再退回）**：这里的循环一开始写成"目录在外、文件名在内"，
> 结果自带的 `AdobeRGB1998-compatible.icc` 会**遮蔽**系统里那份真正的 Adobe RGB(1998)
> —— 因为自带目录永远排在系统目录前面。是自检里"模拟系统目录放一份官方文件、
> 必须搜到它"那条用例抓出来的（把循环顺序改回去，该用例立刻失败）。
> 所以顺序必须是**文件名在外、目录在内**。

**实在一份都找不到时不猜**：报错并把这张图改走 rawpy 全解码（直接输出 sRGB，颜色正确，
代价是每张慢 1–5 秒），日志与结果 warning 里都会写明原因。
（正常情况下不会走到这一步 —— 自带的那份就在包里。）

### 预览提取：为什么回退 rawpy 也要说清原因

rawpy 全解码是真正的慢路径（每张 1–5 秒），而它以前只写一句“较慢”、不写“为什么”，
用户拿日志也查不下去。现在：

- **原因会跟到日志与文件级警告里**：`exiftool 不可用` / `未找到 PreviewImage…` /
  `字节流无法解码为图像（…）` / `缺少源色空间 profile（…）` 四种分开说；
- **exiftool 不可用与标签缺失必须分开**：修法完全不同（一个装 exiftool，一个是文件里真的没有嵌入式预览）；
- **DNG 重新走快路径**：实测 DJI 的 DNG 把 JPEG 放在 `PreviewImage` 里（459 KB 标准 JFIF），
  以前一律不用它 → 每张白等一次 rawpy。现在先问 exiftool “这个标签多大”，
  超过 8 MB（未压缩大位图那一类）就不拿，否则直接用它。
  注意：**体积只是第一道快速拒绝**（防内存被打爆），它不能当“这张预览够不够用”的判据 ——
  体积小也可能是 320×213 的小图。“够不够用”由**实测宽高**判定：
  长边不足目标（1024）的一半就算低可信，会写进文件级警告并让提示词提醒模型克制细节类判断
  （实测：CR3 的 1620×1080 与 DJI 的 960×720 都算够用，320×213 才算小）。

> 实测对比（本机 test_data）：DJI DNG 从「rawpy 1.3 秒 + 一条回退警告」变成
> 「嵌入式预览 0.8 秒 + 无警告」；Canon CR3 仍是 1620×1080 的 `PreviewImage`，0.3 秒。

#### exiftool 与中文路径（踩过，别再改回去）

只加 `-charset exiftool=utf8`，**绝不能加 `-charset filename=utf8`**。

实测（exiftool 13.59，路径 `E:\%同步\R5m2\_G4A0172.CR3`）：

| 参数 | 读 | 写 |
|---|---|---|
| 无 charset | ✅ 正确 | ✅ 真的改动文件 |
| 只 `-charset exiftool=utf8` | ✅ 正确 | ✅ 正确 |
| `filename=utf8` + `exiftool=utf8`（旧写法） | ❌ `rc=1`、`File not found` | ❌ 返回 **0** 但 stderr 写 `Error opening directory`，**文件一个字节没变** |

危害有两层：
1. **读取失败被当成“标签缺失”** → 每一张中文路径的 RAW 都静默回退 rawpy 全解码（慢 1–5 秒/张），
   日志还把原因归错；`test_data` 是纯 ASCII 路径，所以这个缺陷一直没暴露；
2. **写入失败返回 0** → 会把“没写进去”报成成功。所以现在 `Error:` 一律按失败处理
   （`Warning:` 仍然是警告 —— 你自己的 XMP 自带 13 类 `Non-standard XMP property` 警告，
   那是正常的，不能被当成失败）。

> 为什么宁可慢也不能凑合：AI 看的是缩略图。Adobe RGB 的数值体系与 sRGB 不同，
> 同一块"中等红色"在 Adobe RGB 里更"淡"。把它当 sRGB 用 → AI 判成欠饱和 →
> 输出 +Vibrance 补偿 → 该参数作用在 RAW 上会让真实出片**过饱和**。
>
> ⚠️ **实测记录（别再退回）**：Adobe RGB 的判定以前读的是 `exif.get(40965)`，
> 但按 EXIF 标准 InteropIndex 住在 **Interop IFD** 里（0xA005 只是指向它的指针）。
> 手工构造两种布局的 JPEG 实测：标准布局下顶层读法得到 `None`，非标准布局下得到
> 一个 **int 偏移量**（38）—— 都不是字符串，所以**那段判断从来没命中过**，
> 声明 Adobe RGB 的预览一直被当成 sRGB。现在改读 `exif.get_ifd(0xA005)[1]`，
> 由自检 `test_color_management` 守着。

**自带的等效 profile 凭什么可信**：不是"看起来能打开"就算数，自检里用
**另一套独立实现的矩阵运算**复算同一条转换链并逐像素比对
（Adobe RGB gamma 563/256 → XYZ(D65) → Bradford 适应到 D50 → 反适应 → sRGB → sRGB 曲线），
最大通道差必须 ≤ 2（当前实测 **0**）。profile 本身只有 608 字节，
是标准的 ICC v2 矩阵型 monitor profile（`desc` / `cprt` / `wtpt` / `rXYZ` / `gXYZ` / `bXYZ` /
`rTRC` / `gTRC` / `bTRC`），LittleCMS 能直接解析。

> 顺带一个坑：`ensure_icc_assets()` 只在文件**不存在**时写入，
> 所以它不会覆盖 Adobe 官方那份，也不会覆盖你自己放的任何 profile。

### 训练模式

添加若干 (RAW + 其对应 XMP) 对，程序提取预览、把 XMP 转回 JSON，
**区分「你实际调整的参数」与「相机/镜头默认值」**，连同预览图交给 AI 归纳偏好，
产出 `style_profile.json` 存入 `styles/`，由你命名后即可在输出模式的风格下拉中选用。
支持多风格文件互相切换。

> **模型与密钥两种模式共用**：训练同样要调用 AI，所以「模型 / 密钥」两行放在
> 模式切换按钮的下方、**不会被模式切换收起来**，在两个模式下都能直接改。
> 配一次就一直有效。

样本少于 10 张时，**开始训练的那一刻**会弹一次确认框（「样本不足，结果可能不稳定」）
并写进日志，允许你选择继续。这条规则**不会常驻界面**：规则写在代码与文档里，
界面只回答“我现在要做什么”。

训练模式的输入框是**单行**的（它只负责给风格起个名字），调试/排查用的信息
（例如“该模型不支持 json_schema，将用 json_object + 本地强校验”）只进日志，
不当界面文字用。

**训练只发一次归纳请求，但请求预算 ≠ 1**。一次归纳请求里塞着全部样本的参数明细与缩略图，
是最大的一发；首发读超时之后的那次重试（读超时会翻倍）以及解析失败后的修复重试
**都要各花一个预算位**（`TRAIN_REQUEST_BUDGET = 3`）。
> 这条来自一次“静默的训练失败”：44 个样本的首发在 180s 读超时上挂掉，
> 重试被预算（当时是 1）直接拒绝，**风格档案没有保存**，
> 而用户端只看到一个“请求超时”，之后几轮输出用的仍是旧风格 ——
> 他以为已经重训过了。
> 现在的行为：失败时界面显示「训练失败（风格未保存）」，日志明确写
> 「本次训练**没有完成：风格档案没有被保存或更新**」，并给出重试/减样本的建议。

### 提示词与风格：谁说了算

输出模式的提示词优先级**必须是**这样（曾在这里出过一次真实事故）：

| 情况 | 用哪条提示词 |
|---|---|
| 你填了「提示词」 | 用你写的；所选**风格规则同时叠加生效**（风格块照旧注入，不会被提示词挤掉） |
| 没填，但**选了风格** | 程序按风格执行：风格里出现过的分区参数（HSL / 分离色调 / 颜色分级 / 相机校准 / 效果）该用就用 |
| 没填，也**没选风格** | 内置的保守全局校正（统一曝光与白平衡观感，**不做** HSL 与颜色分级） |

> 填了提示词又选了风格时，程序会在提示词后面**显式写一句**
> 「本批提示词与上述风格规则冲突时，以本批提示词为准」—— 风格块里写的是「请逐条遵守」，
> 而它排在提示词**前面**，不给这句优先级，模型会两边各听一半（表现为“只挑了不冲突的那几条做”）。
> 唯一不加这句的情况是风格选了「AI自主决策」：它本来就没有可冲突的偏好规则。

> **为什么要写死这张表**：旧版本写的是 `prompt = 你填的 or 内置保守提示词`，
> 于是「选了风格但没填提示词」时，内置那句「不做 HSL 分区偏移、不做分离色调与颜色分级」
> 会和风格里 21 条规则正面打架 —— 结果只有基本面板被改，
> 用户的评价是「只调整了亮和颜色，我训练里明明有 HSL / 颜色分级 / 蒙版」。

另外，训练算出来的这些**人话特征块**都会原样发给 AI（旧版只发了统计数字表，模型看不出来那是习惯）：
`style_summary` / `hsl_habits` / `saturation_tendency` / `contrast_tendency` /
`shadow_color_cast` / `lens_correction_preference` / `mask_usage`，
外加一句「本风格出现过的面板（不要只调「基本」；但**只在某张图确实需要时**才动对应面板，
不要为了\'用全面板\'而给每张图都加分离色调/晕影）」。

每次输出的日志里会有一行**面板分布**（例如「基本 5/5、参数曲线 2/5、HSL 0/5」），
如果选了风格却一条分区调整都没用上，会额外给一条警告 —— 不用等你发现结果不对再去翻 XMP。

### 风格只决定「方向」，不决定「数值」

这是设计上的硬约束，也是踩过坑之后的结论：

* **力度用档位表达**。训练会按各维度的实际强度把风格归纳成 **1–7 档**（1 最轻、7 最重），
  提示词发的是「本风格的【影调】力度属于 5/7（偏强）」这类**方向性描述**，
  **不发**统计中位数/均值当目标值。
  > 反面案例：同一风格跑一批图，18 份侧车里的同名字段值**完全一样**，
  > 都等于训练统计的中位数 —— 这正是"把统计值当目标值"的症状。
  > 用户后来的原话是「依然是像 HDR 一样的高饱和，和训练集一点都不符」：
  > 拿他的真编辑对照（`test_data` 里他本人的 XMP），同一张图他设 `Shadows2012=+18`，
  > 模型给 `+50`；他设 `LuminanceAdjustmentRed=-28`，模型给 `+20`（方向都反了）。
* **统计表旁边必须写清楚它是参考**。历史统计块里除了照抄禁令，还多两句：
  ① 一句输出前自检（“若你打算给的值正好等于中位数，请停下来按本图实测指标重新判断；
  同一批里不同照片的数值**应当不同**”）；
  ② **样本 ≤2 的字段被逐条标注「只是个别照片用过，不能当成风格特征」** ——
  实测最刺眼的例子是 `Vibrance` 只有 1 个样本（范围 19~19），模型就给每一张都写 19。
  同理，`text_rules` 那段的小标题从「风格规则（请逐条遵守）」改成了
  「风格倾向（**方向参考**：只在这张照片的情况与它相符时才采用）」，
  因为它本来就是从统计里归纳出来的习惯描述，被模型读成"每张都要执行"就会变成固定预设。
* **场景规则只来自你的训练素材**。训练时 AI 先给每张样本打一个场景标签
  （风景（日出日落）/ 人像（环境）/ 夜景弱光…），**同一场景样本 ≥ 3 张**才归纳出一条规则，
  且规则里不含绝对色温（那会被照抄成开尔文值）。
  程序不会替你发明"长曝水面要锐化"这类经验规则。
* **白平衡只统计「相对 as-shot 的偏移」**，并明确要求 AI **逐张独立判断**，
  不许把偏移量当成每张图的目标值。
* **程序侧护栏**（`acb/ai/guardrails.py`，写盘前执行，全部记日志）：
  · 饱和度组总预算（HSL 饱和度 + 振动 + 饱和度 + 颜色分级饱和度）与暗角总预算，超了按比例缩；
  · **极端值必须有依据**：没有风格规则提到它、且样本数 ≤2 或离散度极大时会被夹回，
    并在日志里写明"因为样本只有 N 张，上限已收紧"；
  · **照抄检测**：整批取值完全一样、且正好等于训练统计中心 → 报警（这种情况通常是模型没看图）；
  · 局部调整的可用字段与范围**全部由训练素材统计**，训练里没出现过的局部字段不会被使用。
* 每张照片都会有一行 `[画像]` 日志（风格 / 用到的面板 / 参数 / 曲线 / 局部调整 / 护栏改动），
  批次末尾汇总面板分布 —— 某张图只用了一种参数，一眼就能看出来。

### 相机配置（`crs:CameraProfile`）

取值来源是 **RAW 自身的机内设置**，不是猜的。四种情况分别处理：

| 情况 | 行为 |
|---|---|
| 没有侧车（新建） | 按机内设置写入，例如 `crs:CameraProfile="Camera Portrait"` |
| 侧车里**已经有**这个值 | **原样保留**，哪怕推导结果不同（你选过的才是真相） |
| 侧车是**本程序**建的、但没有这个值 | **补上**（旧版本建的侧车就是这种情况，不用手工删文件重跑） |
| 侧车是别的工具（如 ACR）建的、没有这个值 | 不动（ACR 靠自己的 `crd:` 相机默认基线） |

原因是一个真实事故：你的 `_G4A0172.CR3` 那批照片**没有侧车 XMP**，程序新建的骨架里
没有 `crs:CameraProfile`；而侧车一旦存在，ACR 就按它渲染、**不再回落到“相机默认配置”**
→ 你在 ACR 里看到的色彩配置变成了「Adobe 标准」。
（同一个目录里你自己修过的 10 个 XMP 全都是 `Camera Portrait`，
和相机机内的 `PictureStyle=Portrait` 一一对应 —— 这就是映射表的定标依据。）

| 相机 | 读的标签 | 映射 |
|---|---|---|
| 佳能 | `PictureStyle` | Portrait → `Camera Portrait`（已用你本机 12 个文件逐一对上） |
| 尼康 | `PictureControlName` | Vivid → `Camera Vivid` 等 |
| 索尼 | `CreativeStyle` | Neutral → `Camera Neutral` 等 |

表里没有的（例如佳能自定风格 `User Def. 1`、富士的 `FilmMode` 命名与 ACR 不一致）
**一律不写**，只记一行原因，并在批次结束时提醒你：
「有 N 个新建的 XMP 没能确定相机配置 —— ACR 可能回落到 Adobe 标准，请打开后在「配置文件」里选一次」。
宁可认不出，也不写一个不存在的配置名（那样用户会以为已经设过了，比不写更糟）。

## 关于「哪些参数才算我的偏好」

ACR 会把**全部字段**写进 XMP（包括大量值为 0 的默认项），
所以**"字段出现在设置里"不等于"你调整过它"**。程序用三层差分来判定：

| 层 | 判据 | 说明 |
|---|---|---|
| 1 | `crd:` 命名空间差分 | XMP 里的 `crd:`（camera-raw-defaults）是**相机出厂基线**，`crs:X == crd:X` 即表示你没改过 X |
| 2 | ACR 出厂默认值表 | 例如 `ParametricShadowSplit=25`、`ColorNoiseReduction=25`、`ColorGradeBlending=50` |
| 3 | 批内不变项剔除 | 整批取值完全一致的字段判为默认（能抓住相机写入的非标准默认值） |

**只有「在所有样本里都被排除」的字段才会进 `ignore_fields`。**
若某字段在 10 张里有 8 张是默认、2 张被你明确调过，它会被放进
`partially_default_fields` 而不是 `ignore_fields`——
否则提示词会让 AI 忽略你的真实偏好，那比"漏报"严重得多。

想自己核对统计是否可信，用这个工具（**不调用 AI、不联网**）：

```bat
python tools/style_stats_preview.py test_data
```

它会逐字段打印"判定为你调整"/"判定为默认"及理由，以及蒙版使用统计。

## 断点续跑与失败处理

- **断点键** = `sha256(文件大小 | mtime_ns | 文件名)[:16]`，**不含目录**，
  因此移动或重命名文件夹后依然有效。
- 每张完成即原子落盘（`state/records.json`），所以「停止」后进度天然保留，
  点「续跑」不会重复请求已经成功过的照片。
- **默认是全量重跑，不跳过任何文件**。这是刻意的：用户反馈过"想重跑却被静默跳过"，
  替用户省钱的默认值反而挡住了正常使用。要跳过已完成，请显式点「续跑」
  或加 `--resume`。
- 进度条为收尾阶段（生成脚本 + 调用 Photoshop 导出）预留了 10% 的区间，
  所以**进度条满格 = 真的全部结束**；Photoshop 导出期间会停在 95% 左右。
- 失败记入 `state/failed.json`；同一文件累计失败 **2 次**即永久跳过。
  永久跳过有**逃生舱**：`--clear-failures` 或界面上的「清除失败记录」。
- ⚠ **永久跳过是"任何模式都不会再碰"**（键 = 大小 | 修改时间 | 文件名，**与目录无关**，
  所以把文件换个文件夹也照样认得出）。程序会在两处明确点名它：
  · 运行开始时一条告警：**列出文件名**、上次失败的原因、以及怎么重试；
  · 结束汇总（对话框 / 日志）：`其中 N 个是「此前失败达上限、永久跳过」的…要重试请点「清除失败记录」`，
    并且这张清单会**写进日志文件**（不只是显示在界面上）。
  为什么要这么啰嗦：曾经只报一句「跳过 3 张（共 21 张）」，而用户真正想知道的是
  「哪 3 张、为什么、怎么救回来」——结果就是「DNG 文件依然没有被处理」这种求助。
- 管线输出（扫描到几个、跳过谁、预算、汇总）**同时进界面日志面板与日志文件**，
  两处内容一致：出问题时你把日志文件发过来就够了，不必再回忆界面上显示过什么。
- **成本防护**：单批最大请求数 = 文件数 × 2（含重试），超出则停止并告警。
  这通常意味着存在系统性故障（密钥失效、模型名写错、网络不通），
  继续请求只会白烧钱。

### 一个已知的边界情况：键碰撞

断点键不含目录，所以「同名 + 同大小 + 同 mtime」的文件会算出相同的键。
这在 Windows 上**并不罕见**——文件时间戳粒度受系统时钟限制，
同一时钟滴答内拷贝出来的文件 mtime 完全相同。

程序的处理是：检测到碰撞后读取**内容指纹**（头 64KB + 尾 64KB 的哈希）再分组：

- 内容**不同** → 用内容指纹加后缀消歧（后缀与目录无关，移动文件夹依然稳定）；
- 内容**完全相同** → 判定为真重复图片，共用一次分析结果（省一次 API 请求），
  但**两个副本都会被写出 XMP 并各自导出**。

碰撞发生时日志里会有明确的 WARNING 列出涉及的文件。

> 程序启动时会**自动把它重命名**成 `%APPDATA%\AutoColorDiffusion`（只重命名、
> 不复制不删除），所以已保存的 API 密钥、训练好的风格、断点记录都不会丢。
> 若新目录已存在（已经迁过）则不动作，绝不合并覆盖。
>
> **例外**：API 密钥在 Windows 凭据管理器里的“服务名”也从旧名换成了新名。
> 万一密钥没跟过来，重新粘贴一次即可（密钥本身没有被删除，只是换了条目名）。

（★ = 永不删除；☆ = 关闭程序时自动清理，见下节。
`runs\` 里那一次在"需要手动补跑导出"时会被**保留**，否则整个目录删掉 ——
理由是那时 `run_export.bat` 是你唯一的补救手段。）

想便携使用（数据跟着程序走）：在 exe 同目录放一个名为 `portable.txt` 的空文件，
数据会改写到 `<exe目录>\data\`。

### 日志写到哪里

分两类，**都不在输出（出片）目录里**：

| 文件 | 位置 | 说明 |
|---|---|---|
| `app-YYYY-MM-DD.log` | `<数据目录>\logs\` | 程序自身的运行日志，按日期轮转 |
| `ps_log.txt` | `<数据目录>\runs\<运行标识>\` | Photoshop 导出的逐项日志 |
| `ps_result.json` | `<数据目录>\runs\<运行标识>\` | Photoshop 导出的结构化结果（逐项成败） |

**为什么不在出片目录里**：出片目录是你要交付出去的目录，只该有 JPG。
这两个是软件的记账文件，混在里面既碍事，又会在打包交付时被一起发出去。

它们的路径由 Python 侧算好（会考虑便携模式）写进 `manifest.json` 的
`logPath` / `resultPath`，脚本照着写。文件名不必再带运行标识 ——
每次运行本来就是**独立的目录**（形如 `20260919_130056_f4b8`），
一批对应一个目录，多次运行不会互相覆盖，也不会出现"上次的结果被当成这次的"。

**兜底**：如果把整个脚本目录拷到另一台机器上执行（方式 C），
manifest 里的绝对路径在那边可能建不出来，此时脚本会退回"与自己同目录"并使用
同样的文件名 `ps_log.txt` / `ps_result.json` —— 宁可位置不理想，也不能不留痕迹。
脚本会把**实际**落盘位置写进日志开头，找不到时从那里看。

> ⚠️ `runs\<运行标识>\` 在程序退出时会被清理。要留证据，
> 请在关闭程序之前把它复制出去（或用完成对话框里的「打开脚本目录」当场打开）。

### 退出时清理什么（以及绝不清理什么）

关闭程序时会自动清掉本次运行产生的临时文件，**你不需要手动删**：

| 位置 | 处理 |
|---|---|
| `<数据目录>\runs\<运行标识>\` | **整目录删除**（脚本三件套 + PS 日志与结果）。**例外**：本次导出没成功时保留，见下 |
| `<数据目录>\cache\thumbs\` | **清空**（缩略图缓存，下次自动重建） |
| `<数据目录>\state\_tmp_xmp\` | **清空**（写 DNG 内嵌 XMP 时的中转文件） |

> **为什么有个例外**：自动调用 Photoshop 没成功（或你取消了界面上那个「输出」开关）时，
> `run_export.bat` 是你唯一的补救手段。把脚本删掉等于断了后路，所以那一次会保留。
> 代价是它不会被自动清理 —— 下次运行前你可以手动删掉 `runs\` 下的旧目录。

**明确永不删除**（即使在数据目录内部）：

- `<数据目录>\styles\` —— 你训练出来的风格档案（删了要重新训练，不可再生）
- `<数据目录>\state\records.json` / `failed.json` —— 断点与失败记录
  （删了会失去「续跑」能力与失败历史）
- `<数据目录>\state\endpoint_capabilities.json` —— 已探明的“哪个端点不认哪种
  response_format”（删了就下次重新探一次，会多花 1 个请求，**不影响正确性**）
- `<数据目录>\config\models.yaml` —— 你的模型与网关配置
- `<数据目录>\backups\xmp\` —— **覆盖已有侧车之前自动留的原件**（理由见下）
- `logs\app-*.log` —— **程序运行日志，默认保留**（理由见下）
- 你的照片、旁侧 `.xmp`、出片目录里的任何文件 ——
  清理逻辑根本不会走出数据目录

> **为什么默认保留 `app-*.log`**：它已按 10MB × 5 份轮转，占用有硬上限；
> 而它是出问题时**唯一**的排查线索。真要连它一起删，把
> `acb/cleanup.py` 里的 `DELETE_APP_LOGS` 改成 `True` ——
> 但请想清楚：删掉之后程序下次出问题，你将没有任何日志可查。

> **为什么会有 `backups\xmp\`（重要）**：写侧车时会**覆盖**已有的 `.xmp`，
> 而那个文件里可能有你（或 ACR）辛苦调过的参数。曾经发生过一次真实事故：
> 一批侧车被覆盖后再也拿不回来（用户甚至没有意识到是被程序覆盖的，
> 直到发现"那几张的相机配置全变成 Adobe 标准了"）。
> 现在每次**覆盖已有侧车之前**都会先把它原样复制到
> `<数据目录>\backups\xmp\<原文件名>.<时间戳>.xmp`：
>
> - **只在"目标已存在"时备份**（新建侧车不会产生备份文件）；
> - **同一份原件只备份一次**（不覆盖已有的备份 —— 否则拿到的就是改过的版本）；
> - 备份失败**不会**阻断写入（日志里会警告），但会告诉你备份没做成；
> - 命名带秒级时间戳，反复运行不会互相覆盖。
>
> 想恢复：把备份文件改名成对应的 `<照片名>.xmp`（删掉时间戳那段）放回去即可。
> 这个目录**永不自动清理**。

**这是本项目唯一会删文件的功能，所以做了三层保护**：

1. **白名单**：只清理上表列出的三个位置，没有任何"遍历目录找垃圾"的逻辑
   （`runs\` 下只删**目录**，且会跳过需要保留的那一个）；
2. **根锚定**：每个待删路径 `resolve()` 后必须位于数据目录内、且不属于受保护目录。
   是符号链接或目录联接的**一律拒删**（`rmtree` 在联接上可能把目标目录整个删掉）；
3. **强制关闭时跳过**：工作线程 15 秒没退出就跳过清理 ——
   那时 Photoshop 可能正在导出、正写着自己的日志，删文件既是干扰，
   也可能把唯一能解释失败原因的日志删掉。

想临时跳过清理（例如要人工检查缓存）：设环境变量 `ACB_NO_CLEANUP=1`。

回归测试：`tools/smoke_test.py` 的「退出清理」那一项会把 `%APPDATA%` 指向临时目录，
在里面造出真实结构跑一遍，逐项断言"该删的删了、该留的还在"——
包括用户照片目录在数据目录之外时必须完全不动。

## 配置模型

### 连接：端点 + 密钥 + 备注名（这是「主」）

**你的 base_url 才是事实来源，厂商名只是从它推导出来的显示标签。**
现实里大量用户用的不是官方端点 —— SiliconFlow、one-api / new-api 中转、本地 Ollama / vLLM、
公司内网网关：它们全都走 OpenAI 兼容格式、key 全是 `sk-` 开头，
而且**一把 key 能调十几家的模型**。让这类用户「选一家厂商」，他一选就错：
base_url 是错的，密钥还会被存进别人家的槽位。

所以界面上的第一项是**「连接」**（下拉里显示成 `名字 @ 域名` —— 域名不会撒谎），
点它右边的「＋」新建：

| 你想干什么 | 怎么填 |
|---|---|
| 用官方端点 | 「预设」里挑一家（12 家：DeepSeek / OpenAI / 通义千问 / 智谱 GLM / Google Gemini / Kimi / OpenRouter / Groq / xAI / 豆包（火山方舟）/ 百度千帆 / Perplexity），地址自动填好 |
| 用中转站 / 本地网关 | 预设留空，自己填 `base_url`；key 照填。程序会用它去拉 `/models` |
| 同一家两把密钥（主力 + 备用） | 建两条连接、起两个名字。**密钥各存各的，互不覆盖** |

密钥的账户名规则：

- **出厂连接**（内置那 12 家）：沿用 `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 这类旧账户名 ——
  所以你已经存在 Windows 凭据管理器里的密钥**不需要迁移**；
- **你自建的连接**：`conn:<你起的名字>`。所以「DeepSeek-主力」和「DeepSeek-备用」
  是两把独立的钥匙，永远不互相覆盖。

**两条连接共用同一把密钥时，程序会自己说出来**（密钥状态那一行会变成注意色）：

```
已找到密钥 sk-****a8de（来源：系统密钥链，账户名 OPENAI_API_KEY）。…　
⚠ 与连接「DeepSeek」用的是同一把密钥（同一个账户的额度与限流）；
   要给另一家单独的密钥，请用「＋」新建一条连接再填。
```

为什么要有这个提醒：密钥是**按连接的 `key_env` 各存各的**，程序绝不会拿一条连接的密钥
去给另一条用。但如果你（或历史事故）把同一个值存进了两个槽位，切连接时看到的掩码自然一样 ——
光看掩码分不出「程序复用了一把 key」和「两个槽里本来就是同一个值」，很容易误判成 bug。
现在程序替你比较并明说；值不同、或某条连接根本没密钥时，都不会误报。

连接写在 `%APPDATA%\AutoColorDiffusion\config\connections.yaml`（**只由你自己增删**，
升级程序不碰它）。右键「连接」下拉里的任意一条可以删除；
删狠了也不要紧：**高级设置 → 恢复出厂设置** 会删掉该文件并回到默认那 12 条。
⚠ 该动作会**一并重置密钥、失败记录、缩略图缓存与界面偏好**，所以要弹两次确认
（详见上面菜单表下方的说明）；`styles/` 里训练出来的风格文件不受影响。
删除连接**不会**删掉密钥 —— 重建同名连接后照样能用。

### 请求形状：`api_style`（换模型 ≠ 换协议）

不同家的 HTTP 请求结构**不只是 model 名字不同**：

| 协议 | 请求 |
|---|---|
| OpenAI 兼容（本程序目前**唯一**实现的形状） | `POST /chat/completions`，`model` 在请求体里 |
| Anthropic 原生 | `POST /v1/messages`，结构不同且 `max_tokens` 必填 |
| Gemini 原生 | `POST /v1beta/models/{model}:generateContent`，`model` 在 **URL** 里 |

所以「切模型只改一个字符串」这句话，**只对已实现的形状成立**。配置里的 `api_style`
只接受已实现的形状，写别的会**加载即报错**（而不是运行时发一个形状错的请求出去、
表现为 400 或者更糟：网关成功返回但用了别的模型）。要加新协议，必须新增请求构造分支。

### 各家 API 的请求形状（2026-09 逐条核对官方文档）

「都是 OpenAI 兼容」这句话**只对 URL 和消息结构成立**。同一份请求体换个 `model`
发给另一家，参数名、能不能带温度、输出格式约束的支持程度都不一样 ——
而报错原文（`invalid_request_error: Unsupported parameter`）几乎不会告诉你
"是参数名的问题"，只会让用户以为"这家 API 用不了"。

所以下面这张表是**逐格核对官方文档**（不是猜的）之后写进 `models.yaml` 的：

| 连接 | 输出格式档 | 输出上限用哪个字段 | 发不发 `temperature` | 超时 | 官方依据 / 会撞到的报错 |
|---|---|---|---|---|---|
| DeepSeek | `json_object` | `max_tokens` | 发 | 180s | 官方《JSON Output》只给 `json_object`；不改（它没弃用 `max_tokens`）。思考默认开且推理 token 也算输出 → 60s 不够 |
| OpenAI | `json_schema` | **`max_completion_tokens`** | **不发** | 180s | 推理模型（o 系 / gpt-5 及以后）只认新参数名，且把 `temperature` / `top_p` 列为 unsupported → 发了就 400 |
| 通义千问（百炼） | `json_object` | **都不发** | 发 | 180s | 《结构化输出》："开启结构化输出时，请勿设置 `max_tokens`"（会被截断成非法 JSON）；多模态输入**不支持** `json_schema`。另：密钥分地域，跨区调用直接 401 |
| 智谱 GLM | `json_object` | `max_tokens` | 发 | 180s | 只文档了 `json_object`；`temperature` 区间 (0,1)；思考开关走 `extra_body`（但 **5.3 / 5.3-FLASH 强制思考、官方明文不可关闭**，需要控制耗时就选别的型号）。原生多模态（GLM-5.3-Flash）用 base64 data URL 传图 |
| Kimi（月之暗面） | `json_object` | **`max_completion_tokens`** | 发 | 180s | 官方已把 `max_tokens` 标为 **deprecated**；`json_schema` 要符合它的 MFJS 规范（不符会被拒）；K3 恒开思考。**限流是账户级的**：Tier0（¥0）并发 1 / RPM 3、Tier1（¥50）并发 15 / RPM 100 —— 出厂按 Tier1 跑，切到 Kimi 时那行红字里可一键切换（见「关于限流」）；`kimi-k2.6` 只接受 `temperature=0.6` |
| Gemini | `json_schema` | `max_tokens` | 发 | 180s | 走官方 `/v1beta/openai` 兼容端点 |
| OpenRouter / Groq | 无（提示词 + 本地校验） | `max_tokens` | 发 | 180s | 中转与超快推理端点的格式约束支持不一致，不硬发；超时统一 180s（宁可多等，不要半批失败） |
| xAI | `json_schema` | `max_tokens` | 发 | 180s | —— |
| **豆包（火山方舟）** | `json_object` | **`max_completion_tokens`** | 发 | 180s | 《对话(Chat) API》参数表里 `max_tokens`（默认 4096，「最大回答长度」）与 `max_completion_tokens`（「最大输出长度」）**都在**；豆包自带深度思考（思维链也吃预算），所以取语义为"总输出长度"的那个。模型列表里 doubao-seed 全系带「多模态理解」与「结构化输出」标签 —— 但**没写 `detail`**，所以图里不发这个键 |
| **百度千帆** | `json_object` | `max_tokens` | 发 | 180s | 《文本生成》《视觉理解》用的是同一个 `POST /v2/chat/completions`；`response_format` 在视觉理解页明文写了"支持 ERNIE 4.5 Turbo VL 系列"（正好是我们要用的模型）。上限字段用 `max_tokens`：`max_completion_tokens`（含思维链）官方注了"支持模型见上下文管理"，**不是所有模型都认**。`thinking.enable_thinking` 默认 `false`，不必额外关 |
| Perplexity | 无 | `max_tokens` | 发 | 60s | **无视觉**：选中它会走 caption 降级通道（界面有红字） |

**「可选」和「可空」是两件事（这一节是给改代码的人看的）**：

schema 里"这张图不用调这个字段"有两种表达方式 —— 写 `null`（可空联合），或者干脆**不写这个字段**（可省略）。
不支持联合类型的端点（如 Kimi MFJS）只能用后者，所以程序内部也按"可省略"来实现。
落到校验层，就要求把三种情况分清楚，**它们不是同一件事**：

| 模型返回 | 含义 | 处理 |
|---|---|---|
| 字段缺失 / `params` 为 `null` | 模型没回答（响应被截断、跑偏） | **错误**，触发一次重试 |
| `params: {}` | 明确表示"这张不需要调整" | **合法**（提示词与 schema 都这么写的），记一条警告 |
| 其它类型（数组、字符串） | 格式错 | 错误 |

> 这三态以前被写成了 `if not raw:` 一锅端 —— 于是**本来就调得很好的图会被判失败**、
> 触发重试、甚至整批失败，而它其实是模型的正确答案。已修，并有自检盯着
> （其中包括"键缺失必须仍然报错"这条反向断言：把真失败当成"无需调整"悄悄放过，
> 比误报更危险）。
>
> 某一批里如果有图"一条参数都没提"，日志与完成汇总里会明确说一句
> （`N 张图的响应里没有任何参数（模型表示「无需调整」）…`）：
> 既可能是那些图真的不用调，也可能是模型没看图/没执行风格规则 ——
> 这两种情况在界面上长得一样，只能由程序把可能性说出来。

两个「schema 方言」字段（也是逐家一份，接第五家只改配置、不改代码）：

| `models.yaml` 字段 | 取值 | 现实依据 |
|---|---|---|
| `forbidden_schema_keywords` | 关键字列表，默认空 | 这家**额外**不认的关键字（全局那份是严格模式公认不支持的，见 `ai/schema.py`） |
| `allow_anyof_in_schema` | `true` / `false` | Kimi 的 MFJS 规范**不支持 anyOf** → 它设为 `false`。关掉后 schema 在**生成时**就不产生任何"可空联合"（不是生成后再删——删掉会留下一个没有类型约束的属性），代价是 `json_schema_strict` 会退化为非严格，日志会说明原因 |

> **范围约束被剥掉之后，"不出错值"就只剩本地校验一道防线了。**
> 这不是理论风险：`minimum` / `maximum` 是**我们主动不发给服务端**的，
> 所以 `Highlights2012` 之类的越界值只能靠 `xmp/validator.py` 的
> pydantic 边界 + clamp 拦住。自检里有一条断言专门盯着这件事
> （故意喂一个越界 500 的值，必须被拒）。

三个字段解释「为什么需要它」：

| `models.yaml` 字段 | 取值 | 现实依据 |
|---|---|---|
| `max_tokens_mode` | `max_tokens` / `max_completion_tokens` / `omit` | 同一个「输出上限」在不同家叫不同名字，甚至**一个都不能发**（发了人家的结构化输出就坏） |
| `sends_temperature` | `true` / `false` | 推理模型把采样参数列为 unsupported，发了直接 400 |
| `supports_json_object` | `true` / `false` | 三档里的中间档：服务端只保证"是合法 JSON"，字段结构仍由提示词 + 本地强校验兜住 |
| `sends_image_detail` | `true` / `false` | 图片消息里要不要带 `image_url.detail`。`detail` 是 **OpenAI** 的标准字段，但**不是每家文档都写了**：百度千帆《视觉理解》的 `image_url` 只文档了 `url`，火山方舟可摘录的文档里也没给 `detail`。有些网关对"文档外的字段"是严格拒收的（400），而报错只说"参数错误"，你根本读不出是多了个 `detail` |

> **空响应不再靠猜**：任何一家返回"格式不对/空 content"时，程序先按"提高输出上限"重试，
> 再按"去掉 `response_format`（只靠提示词 + 本地强校验）"重试，并把**结论记住**
> （`state/endpoint_capabilities.json`）——下次不再浪费一次请求。
> 实测触发场景：某些中转站对 `json_schema` 回
> `This response_format type is unavailable now`。

> **发给服务端的 schema 会被"削"到严格模式支持的关键字子集**：`minimum` / `maximum` /
> `minItems` 这类我们用来做本地校验的约束**不会被发出去**（严格模式的白名单里没有它们，
> 发了就是 400），`required` / `properties` / `additionalProperties` / `enum` / `anyOf` 保留。

**你在哪能看见这些设置**：把鼠标停在「模型」下拉的某一项上，提示里就有这一项的
`请求形状 / 输出格式 / 输出上限 / 上下文`（以及它属于哪条连接、走哪个 base_url）。

**回归守卫**：`tools/smoke_test.py` 的「各家请求形状」那一项会**真的构造请求体**，
逐家断言"该发的发了、不该发的一个都没有"（`openai` 只带 `max_completion_tokens` 且不带
`temperature`；`qwen` 两个上限字段都不带；`kimi` 带新参数名；`deepseek` 保持旧名），
并断言发给 OpenAI 的严格 schema 里已经没有 `minimum` 这类关键字。
断言落在**序列化后的字符串**上（`json.dumps`），不只看字典：`{"max_tokens": None}`
在字典层面看着无害，序列化出来是 `"max_tokens": null`，有些网关会因此判 400。

> **空 content / 被截断时的"抬高上限"跟着模式走**：抬高的**值**是模式无关的，
> 但字段名由 `max_tokens_mode` 决定 —— 如果翻的是服务端根本不看的那个字段，
> 现象是"请求照样 200，输出却比原来截得更早"，不报错、只变差。
> 自检直接断言这一点（`openai` 翻 `max_completion_tokens`、`deepseek` 翻 `max_tokens`）。
> `omit` 模式下更是**一次请求都不重发**：请求里没有上限字段，重发必然一模一样地失败，
> 所以直接给出"该模型不支持设置输出上限，请减小输入或分批"这类可执行建议。

> **没有输出上限时会提醒你**：`omit` 模式的代价是单次输出的 token 数完全由服务端决定，
> 所以第一次请求前日志里会有一条醒目的提示（只提醒一次，不刷屏）：
> `… 单次调用输出的 token 数完全由服务端决定 —— 大批量运行请注意账单`。

> **服务端"文档没说、实际不认"的情况也兜得住**：任何一家用 400 明确提到
> `response_format` 时（真实例子：`This response_format type is unavailable now`），
> 程序会去掉这个字段**原地重发一次**，并把结论落盘
> （`state/endpoint_capabilities.json`），之后不再浪费请求去试。
> 触发条件刻意收得很窄：只降级一次、只剥这一个字段、且仅当本次确实带了它。

**「模型」下拉里的顺序是"代次从新到旧"，不是字母序**（`config.model_sort_key`）：
先置顶项，再是该连接在 `default_models` 里声明的顺序，最后按"型号代次"排（同名代次按名字）。
为什么不能用字母序：`-` 的码点小于 `3`，字母序会把 `qwen-vl-max` 排到 `qwen3-vl-plus` 前面 ——
切到「千问」时自动选中**更旧的那一代**，而界面上看起来什么都没发生（静默降级，不报错）。

> 代次的取法：名字里第一个 **1–2 位**数字，且先把日期（`2026-06-15` / `2024-08`）整段抠掉。
> 两条规则缺一不可：没有日期剥离，`fun-asr-flash-2026-06-15` 里的"月"`06` 会被读成第 6 代；
> 没有 1–2 位限制，`model-2026` 这种只有年份的名字会被读成第 2026 代。
> `qwen3.5-vl` 这种小数版本号读到的是 3（不是 3.5）——顺序仍然稳定（3 < 4），只是同代次内靠名字排。
> 这几种形态都有断言钉着（`test_model_generation_sort`），不是"恰好没出错"。

### 模型目录：`models.yaml` 只是「预设模板」（这是「从」）

`config/models.yaml` 只描述**预设**（端点 + 能力 + 密钥账户名），**不写死模型 id**（用户要求「不要占位」）。

**界面上的用法**：在「连接」里选一条（或「＋」新建）→ 在密钥框里填自己的 API key → 点「保存」。程序会：

1. **尽力识别 key 属于哪家**（按下面那张表的形态，只在确定时下结论；认不出就以「连接」下拉里的选择为准）；
2. 把密钥存到**这条连接**的账户名（出厂连接 = `DEEPSEEK_API_KEY` 这类旧名，自建连接 = `conn:<你的名字>`）；
3. **自动调用 `GET {base_url}/models` 拉取这条连接真实可调用的模型列表**，填进「模型」下拉
   （结果缓存在 `discovered_models.json`，**按连接分键**、互不覆盖）；
4. 自动选中这条连接的第一个模型。

下拉里的每一项都是**真实接受**的模型 id，切换模型 = 真实切换请求里的 `model` 字段
（并且会核对服务端回显，见「怎么确认『切换模型』真的生效了」）；
切换「连接」= 换 base_url + 密钥账户 + 模型列表 + 请求形状。

### 怎么确认「切换模型」真的生效了

把「模型」从 V4.1 Flash 切到 V4 Pro，在协议上**只是改了请求体里的一个字符串**。
请求发得出去、返回 200、JSON 也解析得了 —— 但服务端完全可能用的是**另一个**模型
（中转站改路由、把不认识的 id 降级到自己的默认模型）。这种失败在界面上表现为「一切正常」。

所以每次请求都会核对响应里的 `model` 字段（服务端回显），并把结果摊在你看得见的地方：

| 你会在哪看到 | 内容 |
|---|---|
| 日志（运行时实时刷新） | `服务端回显模型：deepseek-v4-pro（本次请求的是 deepseek-v4-pro）` |
| 日志（不匹配时，橙色告警，整批只报一次） | `⚠ 模型不匹配：请求的是 deepseek-v4-pro，服务端回显的是 deepseek-flash。切换可能未生效…` |
| 完成对话框的汇总 | `Token 用量：输入 … token，输出 … token　服务端确认模型：deepseek-v4-pro` |
| 不匹配时的完成汇总 | `…　⚠ 服务端实际使用：deepseek-flash（请求 deepseek-v4-pro，切换可能未生效）` |
| 每个文件开始分析前的日志 | `模型能力：DeepSeek [deepseek-v4-pro] @ https://api.deepseek.com/v1；视觉=支持；…` |

最后一行里的 **`@ <完整地址>`** 很重要：`base_url` 指向中转站或内网网关时，
「我到底在调谁」只有它能回答（只写「DeepSeek」会让人以为在调官方端点）。

> 服务端不回显 `model` 时（部分自建网关会这样），日志会明说
> 「无法核对实际使用的模型」，**不会**假装成「已确认」——
> 「没有证据」和「证据说没问题」必须分开。

首次运行会把配置复制到 `%APPDATA%\AutoColorDiffusion\config\models.yaml`，之后只读用户副本。
旧版那份"OpenAI 兼容（通用占位）"或带占位 id 的配置会在首次加载时自动迁移成新的服务商目录。

**升级老配置（重要）**：配置文件只在缺失时从程序内复制，所以内置目录后来新增的服务商
默认**到不了已有安装**——曾经因此出现过"界面「连接」下拉里只有 OpenAI + DeepSeek 两项"
（内置目录其实已经有 12 家）。现在每次加载都会做一次**外科式增补**：

- 内置有、你的配置里没有的服务商 → 自动补进去（所以你**不需要**删掉 `models.yaml` 重来）；
- 你已经有的条目原样保留（自己改过的 `base_url`、网关地址、`extra_headers` 都不会被冲掉）；
- 增补只在"确实缺服务商"时发生，其余情况一个字都不动（幂等，不会每次启动重写文件）。

> 想禁用某一家：清空它的 `default_models`，或者干脆不填它的密钥即可——
> 内置目录被视为程序能力的一部分，删掉的服务商会在下次加载时被补回来。

程序会按模型能力自动选择通道，并在日志里明确告知：

| 能力 | 影响 |
|---|---|
| `supports_vision: false` | 走 **caption 降级通道**：用本地 numpy 统计量生成的文字描述代替图片，只做曝光/白平衡/对比度/饱和度四类保守判断。精度明显较低 |
| `supports_json_schema: true` | 用 `response_format={"type":"json_schema"}`，服务端按 schema 约束输出（最强，但支持的端点少） |
| `supports_json_object: true` | 用 `response_format={"type":"json_object"}`，服务端只保证“是合法 JSON”，字段结构仍由提示词 + 本地强校验负责 |
| 两个都是 `false` | 不带 `response_format`，纯靠提示词 + 本地强校验降级 |

### 输出格式为什是三档（真实踩过的坑）

DeepSeek 官方文档（`api-docs.deepseek.com` 的《JSON Output》指南）写的是
`response_format={'type': 'json_object'}` —— 它**支持 JSON Output，但不支持 json_schema**。
把它写成 `supports_json_schema: true` 的后果是每张图都先吃一个 400：

```
This response_format type is unavailable now
```

（训练模式直接失败，并且因为每请求都要先错一次，请求数翻倍，
会把后面的文件从预算里挤出去。）

现在有三层保护：

1. **出厂配置写对**：DeepSeek 是 `supports_json_schema: false` + `supports_json_object: true`；
2. **老配置会被自动修正**（见下）；
3. **客户端自带一次性自愈**：服务端用 400 拒绍 `response_format` 时，
   程序会自动去掉它重发一次，并把结果**落盘**（见下），后续请求不再带它。
   这只是兜底 —— 配置写对就不会走到这一步。

### 自愈的结果会记住（`state/endpoint_capabilities.json`）

只在内存里记的话，下次启动又会把同样被拒的字段再发一遍：一次白花的请求，
而且带着 base64 图片（中转站按流量计费时这笔钱花得很冤）。所以自愈成功后程序会写：

```json
{
  "https://你的端点/v1": {
    "rejected_formats": ["json_schema"],
    "last_seen": "2026-09-21T18:04:38",
    "last_evidence": "{\"error\":{\"message\":\"This response_format type is unavailable now\"}}"
  }
}
```

- 位置：`<数据目录>\state\endpoint_capabilities.json`（**运行时状态**，不是你的配置；
  退出清理不会删它，由它自己的意义就是跨启动生效）；
- 下次启动会直接不发那个字段，并在日志里说明“按上次的记录…”；
- **想重新试探就删掉这个文件**（日志里会把路径打出来）；
- 读坏了不会拦任务（当空处理，最多多花一次请求）。

费用意义上的代价很明确：**只有第一次会多花 1 个请求**（必须探一次才知道服务端认不认），
之后都是 0 额外代价。发生在返回 400 时（服务端根本没开始生成），所以不存在“重发已生成的推理”。

### 空 content / 被截断：抬高出上限再试一次

官方文档（DeepSeek《JSON Output》注意事项）明写“使用 JSON Output 时 API 有概率返回空的 content”；
而另一个常见原因是**思考模式的推理 token 也算在 `max_tokens` 里**，推理把额度吃光后就只剩空 content。
两种症状（空 content、`finish_reason=length`）的共同点是：**重发同样的请求基本会再失败一次**，
所以程序不是回灌错误重试，而是把**输出上限翻倍**（一次，上限 `65536`）：

```
第 1 次尝试失败（EmptyContentError）：把输出上限从 16384 抬到 32768 后重试一次。
```

仍失败时给的是可执行的动作（调大 `max_output_tokens` / 关思考模式 `reasoning_effort: none` /
调小 `images_per_request` / 改变输出约束方式），而不是一句“解析失败”。
重试名额硬约束是 1 次，所以升档发生在这一次重试上，不会把“每文件 2 个请求”的预算撑大。

### 能力可以按模型区分：`model_overrides`

同一个服务商下的不同模型能力可以不同，所以能力字段可以在模型粒度上覆盖：

```yaml
  deepseek:
    supports_vision: true
    model_overrides:
      deepseek-v4-pro:
        supports_vision: false     # 官方功能表：V4 Pro 不支持图像理解
```

未写的字段继续继承服务商默认值。写错字段名（例如 `vision`）会**加载即报错**，
不会静默当成“没写”。

**规矩：override 里只放“上游文档说不清、或我们实测过”的差异，并写清依据（`reason`）。**
为什么不硬性要求：加一个必填字段会直接弄挂已有配置；但完全不提，
三个月后没人知道哪条 override 还该不该留。所以取中间：

```yaml
    model_overrides:
      deepseek-v4-pro:
        supports_vision: false
        reason: "DeepSeek 官方《模型 & 价格》页功能表：图像理解 flash 支持、v4-pro 不支持"
```

没写 `reason` 的条目会在日志里提醒一次（不拦加载）。为什么要有这条规矩：
override 很容易长成一个“跟上游文档脱节的本地数据库” ——
今天加 `supports_vision`，明天就会有 `supports_thinking`、`rate_limit`……
而**能从上游文档直接读到的逐模型差异，就该按文档写；写不清依据的，就别加。**

> 实例（DeepSeek 官方「模型 & 价格」页面的功能表）：
> `deepseek-flash`（V4.1-Flash）图像理解**支持**；`deepseek-v4-pro`（V4-Pro-0813）**不支持**。
> 所以程序保存密钥后会**优先自动选中能看图的那个**（本工具的每条链路都靠缩略图判断），
> 并在选中不能看图的模型时用红字明示要走 caption 降级。

> ⚠ **但那个自动选择不会覆盖你的选择**：只有当“这条连接还没选中过模型”或
> “你原来选的那个已不在列表里”时，程序才会替你选；你在下拉里点过的模型
> （哪怕它不能看图、哪怕你就是为了便宜而选它）**永远不会被拉取结果改掉**。
> 真替你换了时，日志里会写清原因。

### 模型自己的旋钮：`extra_body`

各家自己的调优参数不在 OpenAI 的公共字段里，用 `extra_body` 原样合进请求体：

```yaml
    # DeepSeek 的思考模式默认是开的（强度 high）；关掉可以更快出 JSON。
    extra_body:
      reasoning_effort: "none"
```

`model` / `messages` / `stream` / `response_format` 四个键由程序管理，
写进 `extra_body` 会被拒（那不是“微调”，而是改程序的行为，出错时无法归因）。

### 老配置的自动修正（只动你没改过的值）

`models.yaml` 只在首次运行时从内置种子复制一份，之后就是你的文件了。
为了把“我们写错的能力声明”送到已经装好的机器上，程序会在加载时修正**满足全部三条**的字段：

1. 服务商与字段命中内置的修正表（当前只有 DeepSeek 的几项）；
2. 你的值**恰好等于我们当年写错的那个值**（说明是继承来的，你没动过）；
3. 新种子里的值确实不同。

你自己改过的任何值一律不碰。修正会写进日志（`模型配置已修正 N 处…`）。

> ⚠ **这条修正的边界（要知道，别指望它兜住一切）**：判据是"你的值恰好等于我们当年写错的
> 那个值"。所以如果你**自己手动**把某个能力字段改成了别的值（哪怕也是错的），
> 它就不会被自动修正 —— 这是刻意的取舍：宁可漏改，也绝不覆盖你的改动。
> 遇到"我明明改了怎么还是不行"，请对照官方文档自行核对，或者**直接删掉那一行**让它回到默认。

**`connections.yaml` 也一样会跟上**（只限于“从预设继承的能力字段”）：
连接在创建时把预设的能力抄了一份，所以预设改了、老连接不会自己跟着变。
修正的范围严格限定为能力字段（`supports_vision` / `supports_json_schema` /
`supports_json_object` / `max_context` / `max_output_tokens` / `model_overrides` /
`default_models` / `request_timeout_s`），而且只在“值恰好等于字段默认值”时才算“没改过”；
`name` / `base_url` / `key_env` / `preset` 永不被碰，**自建连接（没有预设）完全不动**。
日志里会写清楚改了什么（`连接文件里的 N 处能力字段已跟上预设的修正…`）。

`json_schema_strict` 默认关闭。原因：OpenAI 的 strict 模式要求 schema 里每个属性都出现在
`required` 中，而本工具有约 90 个可写字段，开 strict 会让模型每张图都吐出 90 个字段
（未调整的填 null），单图输出约 1000+ token，成本与延迟都不可接受。
真正的把关者是**本地 pydantic 强校验**（未登记字段、越界值、类型错误都会被拦住并触发重试）。

> 另一个与输出有关的真实风险：**思考模式**。DeepSeek 两个模型默认都开着思考（强度 high），
> 推理 token 也算在 `max_tokens` 里。出厂配置因此把它抬到 16384
> （官方默认：非思考 8K / 思考 64K），避免推理把额度吃光、导致 JSON 被截断或 content 为空。
> 官方《JSON Output》的注意事项里就写了“有概率返回空的 content”——
> 真出现时程序会**抬高出上限重试一次**，并把可执行的动作写进错误里。
>
> 把它抬到 16384 会不会把账单抬上去？**不会**：按实际生成计费，上限不等于花费；
> 它的上限是防“输出装不下”而不是“逼模型多想”。想更省，就在模型条目里把它改小
> —— **这个值在界面上是可见的**：把鼠标悬停在「模型」下拉的任一条目上，
> tooltip 会显示该模型的视觉/输出格式能力、输出上限与上下文长度；
> 每次运行的日志里也有一行 `输出上限=… token`。

> 自检仍然会跑完并给出 **88/88 通过**，但末尾会列出 **11 项未实测**
> （6 项要真实 RAW → 加 `--raw-dir <目录>` 才真的跑；5 项要 `test_data/` 里的样本）。
> 「未实测」= 这条断言**根本没跑过**，不是通过也不是失败 —— 想全部实测，
> 就把自己的测试照片目录传给 `--raw-dir`，并在 `test_data/` 放几张 CR3/DNG/XMP。
>
> 这条纪律是实测踩出来的：早先这些用例在样本缺失时直接**报失败**（还有一个 `iterdir()`
> 抛 `FileNotFoundError` 把整轮打断），把"没有素材"显示成"代码坏了" ——
> 从源码备份里跑自检的人会彻底走错方向。现在一律记「未实测」。

### 应用图标（圆角风格）

图标不是"塞一张图"，而是由脚本**生成**的，产物有三份：

| 文件 | 用途 |
|---|---|
| `assets/icon/app-256.png` | 运行时窗口 / 任务栏图标（圆角、四角透明） |
| `assets/icon/app-512.png` | 大尺寸版，「关于」对话框里显示它 |
| `assets/app.ico` | 打包时给 exe 用，**多尺寸**：16 / 24 / 32 / 48 / 64 / 128 / 256 |

换图标（换成你自己的图）：

```bat
rem 1) 把图片存成 assets\icon\source.png（PNG/JPG 都行，越方越好）
rem 2) 重新生成三份产物
.venv\Scripts\python.exe tools\make_icon.py
```

两个可选开关（源图不一样时才需要）：

| 开关 | 什么时候用 |
|---|---|
| `--no-trim` | 源图本身就是一块完整的圆角方块、四周**没有**独立留白时用。默认会按**四角的底色**把四周留白裁掉（白底、黑底、透明底都认），遇到这种源图会把设计稿的底一起裁掉 |
| `--art-ratio 比例` | 裁掉留白后内容占边长的比例（默认 0.84，即四周各留约 8% 呼吸边）。`1.0` = 内容顶到边；想让图案在大图标里显得更大就调到 `0.9` 左右 |
| `--radius 比例` | 源图自带的圆角弧度跟默认的 22% 明显不一样时用（如 `--radius 0.18` 收小、`--radius 0.26` 放大），让最终圆角与源图对齐、不出现“双圆角” |

> 仓库里现在这三份产物是用 `assets/icon/source.png`（黑底 + 金色圆环/月亮的设计稿）生成的：
> 那张稿子把图案画在中间、四周是大片纯黑（实测 2567×2198 的画布里图案只占 712×736），
> 所以**不需要加任何开关** —— 默认就会按四角底色（黑）裁掉留白，再按 84% 留边补齐正方形。
> 上一版「四个半透明圆」的设计稿保留在 `assets/icon/source-circles.png`，想换回去就
> `--source assets/icon/source-circles.png --no-trim`。

`tools/make_icon.py` 做三件手工做不到位的事：

1. **底色是量出来的、留白按比例留**：先看四角是什么颜色（白底 / 黑底 / 透明底都认），
   把那颜色的整行整列裁掉，再按 `--art-ratio`（默认 0.84）把内容摆进正方形 ——
   内容是长方形时**不拉伸**，四方留边对称，黑底稿也不会凭空长出白边；
2. **每个尺寸单独重采样**（不是把 512 硬缩到 16）：**小于 48px 的尺寸去掉柔光**，其中
   32px 提亮到 1.06 倍、**16/24px 提亮 1.22 倍再膨胀一像素** —— 黑底上的细金线在 16px
   会被重采样削没，靠这手把圆环“找回来”（实测：不加时 16px 只剩一个月牙）；
3. **回读校验**：写完 ICO 会把它读回来确认尺寸齐全，缺了就返回非零退出码
   （"写进去了"和"看起来写了"是两件事）。

> 从源码运行看效果：窗口左上角与任务栏的图标都取自 `assets/icon/app-256.png`。
> 任务栏图标还需要 AppUserModelID 才不会被算成 python.exe —— 这在 `run_app()`
> 里用 `SetCurrentProcessExplicitAppUserModelID` 设好了（必须在建窗口之前设）。
> 打包后 exe 的图标来自 `assets/app.ico`，由 `acb.spec` 的 `EXE(icon=…)` 指定。



> **自检不碰你真实的 API 密钥**：`gui_smoke_test.py` 会把密钥后端整体换成内存实现
> （`_InMemoryKeyring`），任何用例 —— **包括它们的事后清理** —— 都写不到 Windows 凭据管理器。
> 这条纪律是踩出来的：曾有一条用例的清理代码在还原真实后端之后调了 `delete`，
> 真的删掉了用户凭据管理器里的 `OPENAI_API_KEY`（后来靠另一个槽里逐字符相同的值才恢复）。
> 只在用例内部打补丁，永远有"补丁没盖到清理路径"的缝隙 —— 所以改在入口一次性接管。
>
> **自检全程隔离数据目录**：`smoke_test.py` 从第 2 项起、`gui_smoke_test.py` 全程都会把
> `%APPDATA%` 指向**临时目录**（它们真的会写偏好文件、往 styles/ 里放测试风格、
> 还会覆盖侧车因此产生备份文件），跑完不会在你的真实数据目录里留下任何东西。
> 这条纪律有回归验证：跑完自检后比对 `<数据目录>` 的文件快照，必须**零新增、零改动**。
> （曾经不是这样：`--raw-dir` 一跑就往真实 `backups\xmp\` 里塞测试产物，还重写过你的
> `config\models.yaml`。根因是"逐个用例自己隔离"，漏一个也看不出来，
> 现在改成在入口统一兜住。）
>
> 这条纪律现在**每次跑自检都会被断言**：跑之前对数据目录做快照，跑完比对，
> 必须零新增、零改动（`logs\` 除外，那是程序自己在写的轮转日志）。
> 唯一的逃生舱是环境变量 `ACB_TEST_REAL_DATADIR=1` —— 只有"被测对象本身就是真实配置"
> 的排查（例如验证旧配置迁移）才需要它，开启后快照那条断言会如实说明"不适用"。
> **自动化里永远不要设它。**
>
> 排除清单**被钉死在「只有 `logs\`」**（自检里有一条断言盯着它）：
> 一旦"某次写脏了就顺手把那个目录排除掉"成为习惯，排除列表迟早会比被测内容还长，
> 差分就失去意义了。想加第二项，必须显式改那条断言并说明"它为什么属于程序自己在持续写的
> 运行时目录"；如果只是某个用例写脏了，正确做法是**隔离那个用例**，不是豁免它。

### 为什么 `dump_crs_fields.py` 这道门禁很重要

ACR 对**不认识的 crs 字段是静默忽略**的——任务"成功"、参数却没生效，
用户直到出片才发现。所以字段表必须跟得上 ACR 的版本演进。

实际效果：在项目自带真实样本（当时 8 个）上首次运行，门禁报出了 **28 个未登记字段**，
其中几个是真问题：

- `Glow` —— ACR 16.3+ 在「效果」面板新增的「光晕」滑块。不登记，AI 就永远不会提出调整它；
- `Table_A8320194E3EFB1B3FD3D5ACEC3C27E51` —— ACR 承载一段混淆编码数据块的字段，
  名字里的哈希取决于内容，无法预先枚举（现在按 `Table_` 前缀识别）；
- `UprightTransform_0..N` —— Upright 透视校正求出的 3×3 变换矩阵，个数由 `UprightTransformCount` 决定。

补充登记后，门禁在样本上达到 **150/150 通过**（9 个 XMP、共 150 个不同的 `crs:` 字段全部已登记）。

## 打包为 Windows exe

```bat
build.bat
```

脚本会自动：建 venv → 装依赖 → PyInstaller 打包 → 打印产物清单与自验步骤。

产物为 **onedir**（优先于 onefile）：启动快（1–2 秒）、排障容易（缺哪个 dll 一眼可见）、
更新只需替换改动文件。若确实需要单文件：`acb.spec` 里写的是
`EXE(exclude_binaries=True, …)` + `COLLECT(…)` 的 onedir 结构，**不能只改命令行参数** ——
要把 EXE 改成 `exclude_binaries=False` 并删掉 COLLECT（或直接用 PyInstaller 重新生成一份 spec）。
单文件的代价：每次启动都要把整包解压到 `%TEMP%\_MEIxxxx`（首次 10–30 秒），
被杀软反复扫描的误报率更高，且临时目录若被清理策略删除程序会直接起不来。

### 产物清单

```
dist\AutoColorDiffusion\
├─ AutoColorDiffusion.exe            双击运行（无控制台窗口，图标来自 assets\app.ico）
├─ _internal\                    运行库与打包资源（不要删、不要单独移动）
│   ├─ config\models.yaml
│   ├─ styles\default_neutral.json
│   ├─ styles\AI自主决策.json        内置的第二个风格（同样不可删）
│   ├─ assets\icon\app-*.png       应用图标（窗口 / 任务栏 / 关于对话框）
│   ├─ assets\icc\*.icc            程序自己生成的 sRGB / Adobe RGB(1998) 等效 profile
│   ├─ assets\jsx\export_batch.jsx
│   ├─ README.md / NOTICE.txt / LICENSE   说明、致谢与许可（PyInstaller 把 datas 放在 _internal 下）
│   ├─ PyQt6\Qt6\translations\*.qm  右键菜单与标准对话框的中文文案
│   ├─ exiftool.exe + exiftool_files\   整份捆绑的 ExifTool（DNG 内嵌 XMP 读写用）
│   └─ （启动器 exe 在产物里跑不动，程序会自动改用同目录的 perl + exiftool.pl）
├─ README.md                      发布时额外复制到最外层，方便直接阅读
├─ NOTICE.txt
├─ LICENSE                        许可条款（Copyright and Permission Notice v1.0.0）
└─ 构建信息.txt                    版本 / 构建时间 / exe 的 SHA-256
```

> `styles\` 里**只会**有两个内置种子：`acb.spec` 是**逐个列名**加入的，从不整目录打包 ——
> 否则 `ensure_seed_styles()` 会把开发者自己训练/测试的风格释放到每个用户的风格目录，
> 而且 `is_seed_style()` 会让用户删不掉它们。自检里有一条断言盯着这个（名字一改就红）。

### 发布流程（三步，前两步是硬门的）

```bat
rem 1) 打包
.venv\Scripts\python.exe -m PyInstaller --noconfirm --clean acb.spec

rem 2) 守门：必需资源齐不齐、有没有把开发者的东西打进去（非零退出就别发布）
.venv\Scripts\python.exe tools\check_package.py dist\AutoColorDiffusion

rem 3) 写构建信息 + 压成发布包（默认输出到桌面）
.venv\Scripts\python.exe tools\make_release.py
```

第 3 步产出 `AutoColorDiffusion-v<版本号>-win64.zip`（版本号取自 `acb.__version__`，
包内是 `AutoColorDiffusion\` 目录 + README / NOTICE / 构建信息），并打印压缩包的 SHA-256。
为什么选「目录 + zip」而不是单文件 exe 或安装包：单文件每次启动都要解压整个包
（首次 10–30 秒）、被杀软反复扫描的误报率更高；安装包则依赖额外工具链（Inno Setup / NSIS），
且对这类“解压即用”的工具没有增益。zip 发给用户解压即用，也不需要管理员权限。

### 自验要求

1. 本机先跑一遍守门（上面第 2 步）；
2. 把整个 `dist\AutoColorDiffusion` 拷到**没装 Python 的干净 Windows 虚拟机**，
   双击 `AutoColorDiffusion.exe`，添加一个测试目录、勾选「离线调试（演练）」、点开始；
3. 确认日志区跑通、输出目录出现 XMP 与 `export_batch.jsx`。

## 打包后首次运行常见问题

### 杀软报毒 / SmartScreen 拦截

**现象**：Windows Defender、360、火绒等报"木马"或"未知发布者"。

**原因**：PyInstaller 打包的 Python 程序是自解压式引导器，其行为特征
（释放文件、动态加载 dll）与部分恶意软件的打包方式相似，属**误报**。
本程序未做代码签名——签名需购买证书。

**处理**：
- SmartScreen：点「更多信息」→「仍要运行」；
- Defender：`Windows 安全中心 → 病毒和威胁防护 → 排除项 → 添加文件夹`，把程序目录加进去；
- 企业环境若被组策略拦截，需联系 IT 加白名单；
- 若你希望降低误报率，可在有能力时购买代码签名证书并对产物签名。

### 缺少 exiftool

**现象**：日志提示"未检测到 exiftool"，且 DNG 文件处理失败。

**处理**：把 `exiftool.exe` 放到 `AutoColorDiffusion.exe` 同目录（或 `_internal\` 下），
重启程序。程序会优先使用它。见上文「安装」一节。

不装也能用，但：预览提取降级为 rawpy 全解码（每张慢 1–5 秒），
且 **DNG 无法处理**（DNG 的 XMP 在文件内部，只有 exiftool 能安全改写）。

### keyring 失败

**现象**：日志提示"系统密钥链不可用，密钥仅在本次会话内存中保存"。

**处理**：
```bat
python -m pip install --upgrade keyring pywin32
```
若在打包产物中仍失败，通常是打包时漏了 `keyring.backends.Windows`（spec 已包含）。
也可以直接用环境变量绕过：
```powershell
$env:OPENAI_API_KEY = "sk-..."
```

### 点「停止」之后会发生什么

停止是**可控且有边界**的，不是“尽量”：

* **不再发送任何新请求** —— 包括重试、超时后的翻倍重试、解析修复重发、
  以及多图失败后的**拆单重发**。这条之前不成立：停止旗标只在“提交下一个请求组”时看，
  已经发出去的那一组会把自己的重试跑完（甚至一张失败 → 拆成 N 张逐张重发），
  用户看到的就是“点了暂停，失败的几张还在继续重试”（他用 GLM 时发现）。
  现在停止旗标一路传到 HTTP 客户端与适配器，重试前、退避等待期间都会检查。
* **队列里还没开始的请求组会被取消**（不再发出去）；
* **正在飞的那几条**无法从网络上抽回，会等它返回或超时（界面与日志会这么说）；
* **已完成的处理结果保留**，被停止跳过的文件**不算失败**（不会计入“失败 2 次即永久跳过”）。

### ACR 不认 XMP（最需要先排查的一项）

**现象**：程序日志全部成功，输出目录有 XMP，但 Photoshop/ACR 打开 RAW 后画面毫无变化。

**排查顺序**：

1. **Camera Raw 首选项没勾「将图像设置存储在侧车 .xmp 文件中」** —— 90% 是这一条。
   见本文档开头。
2. **XMP 文件名/位置不对**。程序写的是"与 RAW 同目录、同名、仅换扩展名"。
   若你手动移动过文件，XMP 就失联了。
3. **DNG 的旁侧文件被忽略**。若你勾了「DNG 也生成旁侧 .xmp」，ACR 仍会优先读内嵌元数据。
   取消该勾选让程序写回文件内部。
4. **ACR 版本太老读不懂新字段**。程序写入的 `crs:Version="15.0"`。
   `ProcessVersion`（处理版本）的规矩是：**原文件有就原样保留**（那是你 ACR 的事实）；
   **没有就写 `15.4`**（= ACR 界面上的「6 版」）。
   > 【用户 2026-09-24 的真实问题】他在 ACR 里看处理版本显示「1 版」并问为什么不是 6 版。
   > 查下来是旧代码刻意**不写** `ProcessVersion`（当时以为“留空 = ACR 用当前默认版本”），
   > 而这个假设不成立：留空时 ACR 按**最老的 Version 1 (2003)** 解释整包设置 ——
   > 2003 引擎不认高光/阴影/白色/黑色/纹理/去薄雾/颜色分级，**蒙版（需 PV4+）更不会生效**，
   > 所以你看到的成片与写进去的参数对不上。现在新建侧车与 DNG 内嵌包都会写明处理版本。
   若你的 ACR 早于 15.4（不认版本 6），把 `acb/xmp/writer.py` 里的
   `DEFAULT_PROCESS_VERSION` 改成 `"11.0"`（5 版）即可。
   用 `python tools/verify_xmp.py --dump <xmp>` 确认字段确实写进去了。
5. **Photoshop 打开 RAW 走的是 ACR 的"默认设置"**。
   检查 ACR 窗口左下角是否显示相机型号旁边有设置图标；
   或在 ACR 里点「更多图像设置 → 读取设置」。

### 添加图片后程序直接闪退（已修复）

**现象**：点「添加照片」后程序窗口瞬间消失，控制台只留下一行
`NameError: name 'name' is not defined`。

**原因（两个叠加的问题）**：

1. `main_window._append_table_row` 里误写成 `elide_middle(name, 70)`
   （应为 `path.name`）。这类未定义变量只在**运行时**报错，
   导入期与语法编译都发现不了。
2. 更关键的是 PyQt ≥ 5.5 的默认行为：当 Python 异常逃出 Qt 槽函数时，
   PyQt 会调用 `qFatal()` **直接终止进程**——所以用户看到的是闪退，
   而不是一个可读的报错。

**修复**：变量已改正；同时新增了 `_install_exception_guard()`，
把 `sys.excepthook` 与 `threading.excepthook` 替换成
"记录日志 + 弹出可读的错误对话框"，从此槽内异常不再导致进程退出。

**回归防护**：新增 `tools/gui_smoke_test.py`，它会真实构造窗口并
走真实的槽函数路径，把这类"静态检查抓不到、只在运行时爆"的问题挡在提交前。

### 控制台出现 QFont::setPointSize 警告（已修复）

**现象**：

```
QFont::setPointSize: Point size <= 0 (-1), must be greater than 0
```

**原因**：`QFont()` 默认构造出来的对象**没有设定字号**，
此时 `pointSize()` 返回 **-1**（Qt 用 -1 表示"跟随系统默认"）。
原代码写的是 `setPointSize(font.pointSize() + 1)`，于是变成 `setPointSize(0)`。

**修复**：先判断字号有效（`> 0`）再 +1；无效时只保留加粗，不动字号。

### Photoshop 里报「manifest.json 解析失败：json 未定义」（已修复）

**现象**：在 Photoshop 里执行 `export_batch.jsx`（手动，或由 `run_export.bat` 拉起）时弹出：

```
manifest.json 解析失败：json 未定义
```

Python 侧则只能报「完成（结果未知，请查看 ps_log.txt）」（当时日志还写在输出目录里）。

**原因**：Photoshop 的脚本引擎 ExtendScript 只有 **ECMAScript 3**，
而 **`JSON` 是 ES5 才引入的对象** —— 这个引擎里根本没有它。
原脚本直接写了 `JSON.parse(...)`，所以必然抛错。

同一个文件里的 `JSON.stringify(...)` 也踩了同一个坑，而它写在 `catch (e) {}`
里被静默吞掉，于是 `ps_result.json` 从来没被写出来过，
Python 只能含糊地报「结果未知」，把真正的线索完全掩盖了。

**修复**：

- 脚本内嵌了一份最小 JSON 实现（`ACB_JSON_POLYFILL` 区块，含 parse 与 stringify），
  仅在宿主自带原生 `JSON` 时才优先使用它；
- `ps_result.json` 现在**一定会**被写出来，并新增 `fatal` 字段记录致命错误，
  Python 会读出这个字段直接显示原因（不再是「结果未知」）；
- 写结果的动作移到写日志**之前**，且写失败不再被静默吞掉；
- 顺带把这两个文件**移出输出目录**，改写到 `<数据目录>\runs\<运行标识>\`
  （见上面的「日志写到哪里」）——出片目录只该有 JPG；
- 解析失败时，弹窗会附带 `manifest.json` 开头 200 个字符与常见原因清单。

**防复发手段**：`tools/jsx_es3_test.py`。
它把脚本里那段实现**原样抽取**出来（不是抄一份），
放进 Windows 自带的 JScript —— 同为 ES3、同样没有 `JSON` —— 真的跑一遍，
再用真实 manifest 与一批边界用例与 Python 的 `json` 逐项比对。

只靠"读代码检查"是不够的：这类缺陷的特点是 **Python 侧全部自检都是绿的**
（Python 有 json 模块，manifest 生成得完全正确），
问题只在 Photoshop 的脚本引擎里出现，而那个引擎在本机没有可编程入口。

### 质量滑块旁边标红 / 点「开始」时弹出「确认极低画质」（有意设计，不是故障）

**现象**：滑块拉到较低档位时，说明文字变红并出现 `⚠ 极低画质`；
点「开始」时弹出确认框，默认按钮是「返回修改质量」。

**原因**：质量 ≤ 3（0 约等于 libjpeg 5）时会产出肉眼可见的块状伪影。
这个取值**本身是合法的**，Photoshop 会照做，所以程序不禁用它，
但**不允许静默放行**——很可能只是手滑拖到了最左边。

**处理**：

- 确实要极低画质（例如做缩略图）：点「仍然使用（继续）」。
  日志会记录「用户确认按极低画质（PS 刻度 N）继续导出」，事后可追溯这是有意为之。
- 只是拖错了：点「返回修改质量」，把滑块拉回 7 以上即可。
- 想改变告警门槛：改 `acb/constants.py` 的 `PS_JPEG_QUALITY_WARN_MAX`。
  滑块的标红、确认框、命令行警告、以及两个自检脚本的断言全部由它派生。
- 命令行**不会**弹框拦截（无人值守场景弹框会挂死），只打印 `[警告]`。

### 界面上「开始」点了没反应

**现象**：日志区没有新内容。

**处理**：先看是否弹了 API 密钥输入框（密钥链无值时会弹出）；
再看模型配置是否加载失败（顶部环境自检会显示"⚠ 需处理：模型配置"）；
最后确认文件列表里确实有受支持的 RAW（后缀不在白名单内的文件会被跳过并记 WARNING）。

### 某些中文文字看着像「左边被切掉一部分」（已缓解）

**现象**：125%（或其它分数缩放）下，部分标签文字最左边那一笔显得比其它笔画细，
截图裁得紧一点时就像被削掉了一块。

**成因**：CJK 字形的墨迹几乎顶到「笔起点」（实测偏 `-0.6px`），
而 Qt 把控件内容矩形的左侧当作笔起点，于是**最左那一列正好压在控件第 0 像素列上**；
125% 缩放下那一列只有 2 个抗锯齿像素，看上去就像缺了一竖。

**已验证的事实**：墨迹**总量并没有丢**（把绘制起点从 0 挪到 1.2px，墨迹像素总数恒为 156），
右侧也没有截断 —— 所以它**不是**普通的文字截断，靠调宽度、改字号都改不掉。

**处理**：QSS 里给 `QLabel` 统一留了 2px 左右呼吸位
（`acb/ui/widgets.py` 的 `LABEL_TEXT_PADDING`，同一个值也计入了画质说明的最小宽度计算），
让墨迹不再贴着控件边界画；同时把写死宽度的按钮
（`显示` / `保存` / `刷新` 的 `setFixedWidth(48/56)`）改成按字体自适应，
避免以后换字体时**真**被截。变灰表达「不可用」的那几处也补了 `:disabled` 配色，
否则 QSS 里写死的 `color` 不受调色板影响，`setEnabled(False)` 后颜色一点不变。

> 调试这类问题时的两个坑：
> 1. `win.grab()` 得到的是 **1.25 倍设备像素**的图，用逻辑坐标去 `copy()` 会取错区域；
>    截图请用 `win.grab(QRect)`。
> 2. **不要把裁切线正好取在控件边界上** —— 那样会把贴边的墨迹切成"被删了"的假象，
>    看起来像真 bug，其实只是裁图裁的。

### 输入框右键菜单曾经是英文（已修）

**现象**：密钥 / 尾缀 / 输出目录输入框和提示词框上右键，出来的是
`Undo / Redo / Cut / Copy / Paste / Delete / Select All`。

**成因**：这些文案**不在本项目的代码里**，是 Qt 自己提供的（`QLineEdit` /
`QPlainTextEdit` 的标准菜单、`QInputDialog` 的 OK/Cancel、`QMessageBox` 的标准按钮），
不加载 `QTranslator` 就永远是英文。

**处理**：新增 `acb/ui/i18n.py`，启动时装上 Qt 自带的
`qtbase_zh_CN.qm` / `qt_zh_CN.qm`（主窗口构造时调 `ensure_chinese_ui()`，
幂等，任何入口都盖得到），现在菜单是「撤消 / 重做 / 剪切 / 复制 / 粘贴 / 删除 / 全选」，
弹窗按钮是「确定 / 取消」。

> 打包注意：`acb.spec` 把这两个 `.qm` 一起拷进 `PyQt6/Qt6/translations/`，
> 否则会出现"开发时中文、打包后变英文"这种只在成品里露头的缺陷。
> 翻译文件缺失时程序不报错，只是退回英文（不能让锦上添花的功能把程序弄挂）。

## 已知限制

1. **ACR 无官方 CLI**，批量导出必须经 Photoshop。PS 未安装时程序仍会完整产出
   XMP + `.jsx` + `manifest.json` + `run_export.bat`（都在 `<数据目录>\runs\<运行标识>\` 里），
   你可在任意装了 PS 的机器上双击执行 —— 但**要把整个脚本目录拷过去**，
   而且**要在关闭程序之前拷**（否则退出清理会删掉它）；
   日志与结果会写到那台机器的 `logPath` 指定的位置，路径建不出来则退回脚本同目录，
   或者用 ACR/Lightroom 自己批量套用设置后导出。
2. **不尝试用 rawpy 复刻 ACR 渲染**。ACR 的 PV5/PV6 渲染管线是闭源的，
   dcraw 式解码在色调曲线、相机配置文件、镜头 LCP 校正上与 ACR 不同源，
   产出会与你在 ACR 里看到的**不一致**——那属于误导性降级，不如明确交给 Photoshop。
3. **蒙版与局部调整是可选能力，且绝不动你已有的蒙版**。
   训练会统计你的蒙版习惯（占比 / 每张个数 / 类型）；只有当**训练素材里带蒙版的照片占比 ≥ 40%**
   时，才允许 AI 在输出阶段提蒙版，每张最多 3 个，只支持线性渐变 / 径向渐变 / 画笔三种
   （`Mask/RangeMask`、`Mask/Image` 生成不了，只能原样保留）。
   提示词里把三种几何的写法写得死死的（并且**给示例**，只写字段说明不管用）：
   `linear` → `zero`/`full` 两个 `[x, y]`；`radial` → `rect` `[上, 左, 下, 右]`；
   `brush` → `dabs` 落点数组。解析器对实测中模型爱犯的两种错做了容错：
   **画笔只给 `rect`** → 在该区域铺 5×5 网格落点；**线性只给 `rect`** → 仅当区域**贴着画框边缘**时
   按「从贴边侧朝对侧衰减」接受（不贴边就方向不明，宁可丢弃）；两种容错都会在日志里写明怎么解释的。
   可用的局部字段与范围、每张图的合计上限，全部由**你自己的训练素材**统计得出 ——
   训练里没出现过的局部字段不会被使用。范围是**两层**的：
   · **习惯范围（软）**给你看、发给 AI 参考 —— 你自己哪些滑块用到多大；
   · **留余量后的硬范围**是写盘时的裁决线 —— 略微超出习惯范围会**放行**（只记一笔日志），
     超出太多才夹回。余量按样本数给（样本少则宽），所以只有 2 张样本的字段不会被卡死。
   局部降噪、局部颜色分级、去边、颗粒、摩尔纹**不对 AI 开放**（技术校正或易被照拄的方向）。
   目标照片**只要已经有蒙版组，程序整组保留、一个字段都不改**（宁可少做，也不破坏你的成果）。
   若风格本来就用蒙版（占比 ≥ 40%）而这一批**一个都没拿到**，批次末尾会给一条可见告警
   （同时进界面与文件日志）—— “没有蒙版”不会再是一件静默的事。
   > 这一条是被真实投诉换的：当时系统提示词里有一句旧话
   > 「蒙版/局部调整的那一组字段也一律不要返回：局部效果由程序按场景生成」，
   > 与风格块里的「请用响应里的 masks 字段提出来」直接矛盾，模型听系统提示词的，
   > 结果连着几轮“一个蒙版也没有”，而日志里一个字都不提。
4. **机器/版本相关字段只保留、不生成**：`ProcessVersion`、`CameraProfile`、
   `LensProfile*`、`Version`、`CompatibleVersion`、`UprightTransform_*`、`Table_*` 等。
   让 AI 写这些会导致跨机器渲染不一致（换台机器可能找不到对应配置文件）或整份设置失效。
   **例外一**：`CameraProfile` 会按相机机内设置推导后写进去，
   它不是 AI 选的（AI 依然被禁止返回该字段），见「相机配置」。
   **例外二**：`ProcessVersion`（处理版本）在**原文件没有该字段时**会被补写为
   `15.4`（= 6 版）；已有值一律保留。不写它的代价是 ACR 把整包设置当成
   「1 版（2003）」渲染 —— 高光/阴影/蒙版全部失效（见「ACR 不认 XMP」第 4 条）。
   另一个例外是 `LensProfile*` 里的**开关**（`LensProfileEnable` / `AutoLateralCA` /
   去色差三组 / 镜头晕影 `VignetteAmount`）：程序按**每张照片自己的基线**补缺
   （该照片的侧车 → 机内 `crd:` 默认 → 两者都没有时按 ACR 默认），
   但**永远不写配置文件名 / 摘要 / 指纹** —— 那必须由 ACR 用自己匹配到的那份 profile 填。
5. **导出格式只有 JPG 和 PNG**（不提供 TIFF，原因见「导出格式与文件名尾缀」）。
6. **只实现了 OpenAI 兼容的请求形状**（`api_style: openai`）。
   内置的 12 家全部走这个形状（Gemini 用它官方的 `/v1beta/openai` 兼容端点）；
   Anthropic 原生 `POST /v1/messages`、Gemini 原生 `:generateContent` **都没实现** ——
   配置里写这两种形状会在**加载时**直接报错，而不是运行时才发出一个形状错的请求。
7. **不支持 macOS / Linux**。非 Windows 平台上程序会抛出 `NotImplementedError` 并说明原因。
8. **降噪不由 AI 决定**。`LuminanceSmoothing` / `LuminanceNoiseReduction*` /
   `ColorNoiseReduction*`（全局 6 个）与局部明亮度降噪都不在 AI 可写字段里 ——
   它们取决于 ISO / 机身 / 曝光时长，看缩略图判断不了。
   你已有的降噪设置原样保留，程序不改、也不让模型提。
9. **限流不由你说了算**。每个连接的 `max_concurrency` / `max_rpm` 只是"我期望的上限"，
   程序会与 429 原文里学到的服务端真值**取更严的一个**；
   并发被压到 1 时批量会明显变慢（例如 Kimi Tier0 就是 1 条一条来）。
   账户档位（Kimi 的 Tier0/Tier1）**程序查不到**（官方没这个接口），所以出厂按 Tier1 跑，
   是否切换由你在界面上点那行红字里的链接决定。

> 降噪、镜头与相机配置、蒙版结构字段一律不允许 AI 写。

| 面板 | 代表字段 | 范围 |
|---|---|---|
| 白平衡 | `Temperature` / `Tint` | 2000–50000K / -150–150 |
| 基本 | `Exposure2012` | -5.00 – +5.00 EV |
| 基本 | `Contrast2012` `Highlights2012` `Shadows2012` `Whites2012` `Blacks2012` | -100 – +100 |
| 基本 | `Vibrance` / `Saturation` | -100 – +100 |
| 效果 | `Texture` `Clarity2012` `Dehaze` `Glow` | -100 – +100 |
| 色调曲线 | `ToneCurveName2012` | Linear / Medium Contrast / Strong Contrast / Custom |
| 色调曲线 | `ToneCurvePV2012`(+R/G/B) | 元素型，0–255 整数点，2–16 个 |
| HSL | `HueAdjustment*` `SaturationAdjustment*` `LuminanceAdjustment*` | -100 – +100（8 色 × 3 组） |
| 分离色调 | `SplitToningShadowHue` / `SplitToningHighlightHue` | 0–360（**绝对角**，勿与 HSL 的 -100–100 相对量混用） |
| 颜色分级 | `ColorGrade{Midtone,Shadow,Highlight,Global}{Hue,Sat,Lum}` | Hue 0–360 / Sat 0–100 / Lum -100–+100 |
| 镜头校正 | `LensProfileEnable` / `LensManualDistortionAmount` / `AutoLateralCA` / `VignetteAmount` | 0–1 / -100–+100 / 0–2 / -100–+100 |
